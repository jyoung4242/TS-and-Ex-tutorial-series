Introduction

TypeScript errors feel intimidating at first because they're verbose and precise in ways plain JavaScript never was. That precision is the point. TypeScript is not scolding you — it's giving you a detailed, machine-readable description of a contract violation so you can fix it without guessing. The skill is learning to extract the signal from the noise.

Once you can read a TypeScript error, it becomes a precise instruction rather than a wall of red text. This lesson teaches you the anatomy of an error, the small set of error codes you'll see over and over again, and a repeatable strategy you can apply to any error you encounter — even ones you've never seen before.

Anatomy of a TypeScript Error

Every TypeScript error has three parts, always in this order:


// Format:
// FILE(LINE,COL): error TS####: Human-readable description
//
// Real example (what you'd see if you assigned a plain string to a Color property):
// Type 'string' is not assignable to type 'Color'.(2322)
// index.d.ts(12679, 3): The expected type comes from property 'color' which is declared here on type 'ActorArgs'

Break it down:

  • index.d.ts(12679, 3) — The file, line number, and column. Go here first. This is exactly where TypeScript stopped trusting your code.
  • error TS2322 — The error code. A stable, searchable number. Every TypeScript error has one. More on this below.
  • The description — Plain English (mostly). Read it literally. TypeScript is telling you what it expected and what it actually found.
💡
Tip

Search the error code — not the full message — when Googling. TS2345 returns thousands of solved examples. The full message often contains your specific type names, which confuse search engines.

The Most Common Errors You'll See

You will encounter a small set of error codes over and over again. Recognizing them on sight saves enormous time. Here are the five you'll meet most often in Excalibur game development: 


// TS2345 — Wrong argument type
function moveActor(speed: number) { /* ... */ }
moveActor("fast"); // ❌ TS2345: 'string' is not assignable to 'number'

// TS2339 — Property doesn't exist on a type
const actor = new ex.Actor();
actor.spreed = 100; // ❌ TS2339: Property 'spreed' does not exist on type 'Actor'
                    //           (it's 'vel', not 'spreed' — a typo!)

// TS2322 — Assigning the wrong type to a variable
let health: number = 100;
health = "full"; // ❌ TS2322: Type 'string' is not assignable to type 'number'

// TS7006 — Implicit 'any' (parameter with no type annotation)
function takeDamage(amount) { // ❌ TS7006: Parameter 'amount' implicitly has 'any' type
  health -= amount;
}

// TS2554 — Wrong number of arguments
function spawn(x: number, y: number) { /* ... */ }
spawn(100); // ❌ TS2554: Expected 2 arguments, but got 1
ℹ
Note

TS2339 (property doesn't exist) is the single most useful error for catching typos. If you mistype a method or property name, TypeScript catches it immediately. JavaScript would silently return undefined and let you spend an hour debugging.

A Strategy for Reading Any Error

When you hit a TypeScript error you don't immediately recognize, work through these steps in order. This process works regardless of the error code — use it every time until it becomes instinct.

  1. Go to the location. Open the file at the line and column number. Don't read the full error message yet — just get your eyes on the code.
  2. Read the description literally. TypeScript says exactly what type it expected and what type it received. Map those two things onto the code in front of you.
  3. Hover in your editor. In VS Code (and the Playground), hovering over a red-underlined token shows the full error inline — often with more context than the terminal output.
  4. Search the error code. Copy just TS#### into Google or the TypeScript error reference. Read one or two examples to confirm you understand the pattern.
  5. Fix the nearest thing first. TypeScript errors can cascade — one wrong type upstream causes five errors downstream. Fix the first error in the list, recompile, and see how many disappear before tackling the rest.
⚠
Warning

Don't silence errors with // @ts-ignore or by casting everything to any just to make the red go away. You're not fixing the problem — you're hiding it. TypeScript errors that get suppressed have a way of becoming runtime bugs at the worst possible moment.

Errors vs. Warnings

TypeScript output distinguishes between errors and warnings. Errors block compilation — your code won't run. Warnings surface in your editor but don't stop the build. 


// An error — compilation stops:
const x: number = "hello"; // TS2322

// A warning — runs, but your editor will flag it:
const unused = 42; // TS6133: 'unused' is declared but its value is never read
                   // (only a warning in many tsconfig setups)

In the Playground, anything underlined in red is an error you need to resolve before Run will produce a working game. Underlined in yellow is a warning — worth addressing, but it won't stop your game from starting.

📌
Remember

TypeScript errors are not personal. They mean the compiler gathered enough information to tell you something is wrong before your game crashes. Every error you read and fix is a runtime bug that never happened.

🏆 Challenge
Cascade Hunting

Change the type of a variable that's used in multiple places — for example, declare a variable as string that currently holds a number and is passed to several functions. Count how many errors appear. Fix only the root cause (the variable declaration) and see how many downstream errors vanish automatically. This is the "fix the first error" strategy in action.

Summary
  • Every TypeScript error has three parts: a file/line location, an error code (TS####), and a plain-language description. Always start with the location.
  • The most common errors are TS2345 (wrong argument type), TS2339 (property doesn't exist — great for catching typos), TS2322 (wrong assignment type), TS7006 (implicit any), and TS2554 (wrong number of arguments).
  • When stuck, search the error code, not the full message. Fix errors from the top of the list down — one upstream fix often collapses several downstream errors.
  • Errors block compilation and must be resolved. Warnings surface in the editor but won't prevent the game from running.
  • Don't suppress errors with @ts-ignore or any. TypeScript errors are advance warnings of runtime bugs — fix them, don't hide them.

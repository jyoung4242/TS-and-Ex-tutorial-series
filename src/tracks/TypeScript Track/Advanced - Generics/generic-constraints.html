Introduction

Generics let you write code that works with many types at once. But sometimes any type is too broad. If you write a function that reads the .name property from its argument, a bare T will not do: TypeScript has no reason to believe T has a name property at all, and it will refuse to compile the access. Generic constraints solve this by letting you say "T can be anything, as long as it satisfies this shape."

This is the difference between a generic that is merely flexible and one that is actually safe. Constraints let the compiler help you without forcing you to abandon the reusability that made you reach for a generic in the first place.

Before you start

This lesson builds on the Generics in Functions lesson. Make sure you are comfortable writing a basic generic function signature (function identity<T>(value: T): T) before continuing.

The Problem with Unconstrained Generics

Consider a function that is supposed to log the name of any game entity. A first attempt might look like this:


// BROKEN: TypeScript does not know T has a "name" property
function logName<T>(entity: T): void {
  console.log(entity.name); // Error: Property 'name' does not exist on type 'T'
}

TypeScript refuses because T could be a number, a boolean, or anything else that has no name. The compiler is protecting you from a runtime error you would only discover during a game session.

⚠
The any escape hatch is not the answer

You could cast entity to any to silence the error, but that throws away type safety everywhere the function is used. Constraints are the right tool here.

Constraining with extends

The extends keyword in a type parameter position means "T must be assignable to this type." It does not mean inheritance the way it does in a class definition. Think of it as a minimum-shape requirement. 


// Declare a minimal shape
interface Named {
  name: string;
}

// T must be a type that has at least a "name: string" property
function logName<T extends Named>(entity: T): void {
  console.log(entity.name); // Safe now: TypeScript knows name exists
}

// Works: object satisfies the Named shape
logName({ name: "Player", health: 100 });

// Error: number does not have a "name" property
logName(42);

The call site still infers T from the argument. If you pass an object with extra properties, TypeScript keeps track of those too. The constraint is a floor, not a ceiling. 


interface Named {
  name: string;
}

function cloneWithTag<T extends Named>(entity: T, tag: string): T {
  return { ...entity, name: `${entity.name} [${tag}]` };
}

const enemy = { name: "Goblin", health: 40, speed: 2 };
const tagged = cloneWithTag(enemy, "elite");
// tagged is still { name: string; health: number; speed: number }
// The full shape of T is preserved
console.log(tagged.speed); // 2 — no information is lost
💡
Return type follows the input type

Because the return type is T (not just Named), callers get back the specific type they passed in, including any extra properties. If you returned Named instead, those extra properties would be hidden from callers.

Combining keyof with Constraints

A very common pattern pairs two type parameters: one for an object type and one constrained to be a key of that object. This lets you write a safe property-access helper that TypeScript can reason about completely. 


// K must be one of the actual keys of T
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const actor = { name: "Hero", x: 100, y: 200 };

const name = getProperty(actor, "name"); // type: string
const x    = getProperty(actor, "x");    // type: number

// Error: "speed" is not a key of typeof actor
getProperty(actor, "speed");

The return type T[K] is an indexed access type. It resolves to whatever type that key actually holds, so you get precise inference at the call site, not a vague string | number | boolean union.

📌
keyof produces a union of literal key types

For { name: string; x: number }, keyof produces "name" | "x". Constraining K extends keyof T means TypeScript will reject any string that is not literally one of those keys at compile time.

Multiple Constraints

A type parameter can only have one extends clause, but you can express multiple requirements by intersecting the constraint types with &. 


interface Named {
  name: string;
}

interface Positionable {
  x: number;
  y: number;
}

// T must satisfy both Named AND Positionable
function describeEntity<T extends Named & Positionable>(entity: T): string {
  return `${entity.name} is at (${entity.x}, ${entity.y})`;
}

// Works: object has name, x, and y
describeEntity({ name: "Slime", x: 50, y: 75, health: 10 });

// Error: missing x and y
describeEntity({ name: "Ghost" });
💡
Prefer narrow constraints

Only constrain what your function body actually needs. A constraint that requires too much forces callers to build objects that satisfy unnecessary properties, which reduces reusability. Ask yourself: "Would the function body break if I removed this constraint?" If not, remove it.

Default Type Parameters

TypeScript also allows you to give a type parameter a default, using = SomeType after the constraint. This is useful when a generic function or class has a natural "common case" type that callers do not need to specify every time. 


interface ActorConfig {
  name: string;
  color?: string;
}

// T defaults to ActorConfig when the caller does not provide a type argument
function createActor<T extends ActorConfig = ActorConfig>(config: T): T {
  return { color: "white", ...config };
}

// TypeScript infers T = ActorConfig, no explicit type argument needed
const hero = createActor({ name: "Hero" });

// Caller can still provide a more specific type
interface EnemyConfig extends ActorConfig {
  damage: number;
}

const goblin = createActor<EnemyConfig>({ name: "Goblin", damage: 5 });
console.log(goblin.damage); // 5
ℹ
Default vs constraint

The default (= ActorConfig) is what TypeScript uses when no argument is supplied. The constraint (extends ActorConfig) is what TypeScript enforces regardless. They are independent: you can have a constraint without a default, a default without a constraint, or both together as shown above.

Generic Constraints in an ExcaliburJS Context

ExcaliburJS uses generics extensively in its Actor and component APIs. You will often write helper utilities that should work with any Actor subclass. Generic constraints let those helpers remain reusable without sacrificing the type information that subclasses carry. 


import { Actor } from "excalibur";

// Constrain T to any Actor or Actor subclass
function resetPosition<T extends Actor>(actor: T): T {
  actor.pos.x = 0;
  actor.pos.y = 0;
  return actor; // returns the specific subclass, not just Actor
}

class Hero extends Actor {
  sword: string = "iron";
}

const hero = new Hero();
const reset = resetPosition(hero);
console.log(reset.sword); // "iron" — Hero-specific property is still visible

Without the constraint, TypeScript would not know that T has a pos property. With T extends Actor, it can verify the access and still give callers back their specific subclass type. 


import { Actor } from "excalibur";

// A utility that reads any property from any Actor subclass
function readActorProp<T extends Actor, K extends keyof T>(
  actor: T,
  key: K
): T[K] {
  return actor[key];
}

class Enemy extends Actor {
  damage: number = 10;
}

const goblin = new Enemy();
const dmg = readActorProp(goblin, "damage"); // type: number
const posX = readActorProp(goblin, "pos");   // type: Vector

Summary
  • The extends keyword in a type parameter sets a minimum shape that any supplied type must satisfy, turning a permissive generic into a safe one.
  • Constraints are a floor, not a ceiling: callers can pass richer types than the constraint requires, and TypeScript preserves that extra information through the function.
  • Pairing K extends keyof T with an indexed access return type T[K] gives you a fully type-safe property accessor with no casting required.
  • Multiple requirements are expressed by intersecting constraint types with &, since a type parameter can only have one extends clause.
  • Default type parameters (= SomeType) complement constraints by providing a fallback when callers do not supply an explicit type argument.
  • In ExcaliburJS, constraining helpers to T extends Actor lets utility functions work across all Actor subclasses while keeping subclass-specific properties visible to callers.

Introduction

You have already seen that TypeScript lets you annotate what goes in and what comes out of a function. But there is a gap: what do you do when the relationship between input and output matters more than the specific type? If a function receives a value and returns that same value, the caller should get back exactly what they passed in, not a vague unknown or a union that forces them to narrow later.

Generic functions solve this. They let you write one function that works across many types while keeping the type connection intact. You use them constantly in game code: fetching a component of a known type from an entity, creating a pool of homogeneous actors, reading a config value from a typed store. Understanding generics is the step that turns "TypeScript kind of works" into "TypeScript actually helps."

The Problem Generics Solve

Imagine you want a function that picks the first item from an array and returns it. Here are three ways you might try to write it before knowing about generics: 


// Attempt 1: hardcoded type — only works for numbers
function firstNumber(arr: number[]): number {
  return arr[0];
}

// Attempt 2: any — throws away all type information
function firstAny(arr: any[]): any {
  return arr[0];
}

// Attempt 3: unknown — safer than any, but callers must narrow before using
function firstUnknown(arr: unknown[]): unknown {
  return arr[0];
}

None of these is ideal. Hardcoding a type means writing a duplicate function for every type you need. Using any or unknown means the caller loses the information the compiler already had.

What you actually want is: "whatever type the array holds, return one of those." That is exactly what a type parameter expresses. 


// The generic version — works for any array, preserves the element type
function first<T>(arr: T[]): T {
  return arr[0];
}

const n = first([10, 20, 30]);       // TypeScript infers T = number; n is number
const s = first(["a", "b", "c"]);   // T = string; s is string
const actor = first(scene.actors);  // T = Actor; actor is Actor
💡
Type inference at the call site

You rarely need to pass the type argument explicitly (e.g. first<number>([1, 2])). TypeScript infers T from the argument you pass. Explicit type arguments are useful when inference cannot do the job, which you will see with constrained generics below.

Anatomy of a Generic Function

There are three moving parts: the type parameter list, the parameter types, and the return type. Each one can reference the type parameter. 


//  (1)   (2)       (3)
function wrap<T>(value: T): { wrapped: T } {
  return { wrapped: value };
}

// (1) <T> declares the type parameter — T is a placeholder resolved at call time
// (2) value: T — the argument must match whatever T turns out to be
// (3) { wrapped: T } — the return type is tied to the same T

Type parameter names are just identifiers. T is conventional for a single generic type. When a function has multiple type parameters, names like K and V (key/value) or TInput and TOutput add clarity. 


// Two type parameters: input type and output type are independent
function transform<TIn, TOut>(value: TIn, fn: (v: TIn) => TOut): TOut {
  return fn(value);
}

const length = transform("hello", (s) => s.length); // TIn = string, TOut = number

Constraining Type Parameters with extends

A bare T can be anything: string, Actor, null, a plain object, or a function. That means inside the function body you cannot safely access any properties, because TypeScript cannot know they exist.

Use extends in the type parameter to tell TypeScript the minimum shape T must have. The function still works for any type that satisfies the constraint, but now the compiler knows what properties are available. 


// Without a constraint — accessing .name is an error
function printName<T>(item: T): void {
  console.log(item.name); // Error: Property 'name' does not exist on type 'T'
}

// With a constraint — T must have at least a name property
function printName<T extends { name: string }>(item: T): void {
  console.log(item.name); // OK
}

// Works for any object that has a name string
printName({ name: "Player", health: 100 }); // "Player"
printName({ name: "Goblin", speed: 80 });   // "Goblin"

In ExcaliburJS, this pattern appears whenever you work with entities and their components. Excalibur actors all share a common base, so a generic constrained to Actor lets you write helpers that work on any actor subclass. 


import { Actor } from "excalibur";

// A helper that logs diagnostic info for any actor subclass
function logActorState<T extends Actor>(actor: T): void {
  console.log(`${actor.name} pos=(${actor.pos.x}, ${actor.pos.y}) vel=(${actor.vel.x}, ${actor.vel.y})`);
}

class Player extends Actor { /* ... */ }
class Enemy extends Actor { /* ... */ }

const player = new Player({ name: "Player" });
const goblin = new Enemy({ name: "Goblin" });

logActorState(player); // works
logActorState(goblin); // works
⚠
Constraint vs. parameter type

function foo<T extends Actor>(a: T) is not the same as function foo(a: Actor). The generic version preserves the specific subtype at the call site, so the return type can also be T (the subclass), not just Actor (the base). Use the generic form when the caller needs the specific type back.

Preserving Types Through Return Values

One of the most common reasons to reach for a generic is to make the return type reflect the input type. A typed component getter is a classic example: you pass a component class, you want back an instance of exactly that class, not a generic Component base. 


import { Actor, Component } from "excalibur";

// A typed getter: pass a component constructor, receive an instance of that component
function getComponent<T extends Component>(
  actor: Actor,
  ComponentClass: new () => T
): T | undefined {
  return actor.get(ComponentClass);
}

class HealthComponent extends Component {
  hp = 100;
}

const player = new Actor();
const health = getComponent(player, HealthComponent);
// health is HealthComponent | undefined — not Component | undefined
// So health?.hp is valid without a cast
📌
Constructors as type arguments

new () => T is the type of a class constructor that produces a T. Passing a class itself (not an instance) as an argument lets TypeScript tie the return type to whichever specific class you passed. This is a key pattern for factories and registries.

Generic Arrow Functions

Arrow functions can also be generic. The type parameter goes before the parameter list, just before the opening parenthesis.


// Generic arrow function
const identity = <T,>(value: T): T => value;
//                 ^
//                 Note the trailing comma — required in .tsx files to distinguish
//                 from a JSX element. Safe to include in plain .ts files too.

// Works identically to the function keyword version
const n = identity(42);        // T = number
const s = identity("hello");   // T = string


// A typed entity factory as an arrow function
const createActor = <T extends Actor,>(
  ActorClass: new (config?: unknown) => T,
  config?: unknown
): T => new ActorClass(config);

class Coin extends Actor { value = 10; }
const coin = createActor(Coin); // coin is Coin, not Actor
console.log(coin.value);        // 10 — no cast needed

When Not to Use Generics

Generics add power but also complexity. Reach for them only when there is a real relationship between the types of two or more values (usually input and output, or two inputs). 


// Unnecessary generic — T is used only once, not connected to anything else
function logValue<T>(value: T): void {
  console.log(value);
}

// Better — unknown or a union is fine when there is no type to preserve
function logValue(value: unknown): void {
  console.log(value);
}

A quick test: if removing <T> and replacing it with unknown (or a union) loses no information for the caller, you probably do not need a generic.

💡
Generics vs. overloads

Use overloads when the shape of the function changes based on argument types (different parameter counts or fundamentally different return structures). Use generics when the function logic is identical across types and you just want the type to flow through.

Summary
  • Generic functions use a type parameter like <T> to express a relationship between argument types and return types without hardcoding any specific type.
  • TypeScript infers the type argument from the value you pass at the call site, so you rarely need to write fn<number>(...) explicitly.
  • The extends keyword constrains a type parameter to a minimum shape, letting you safely access properties inside the function body while still accepting any compatible subtype.
  • Passing a class constructor as a new () => T argument lets you write typed factory and registry helpers that return the specific subclass, not just the base type.
  • Generic arrow functions follow the same rules as function declarations; add a trailing comma after the type parameter when writing them in .tsx files.
  • Reach for a generic when the type needs to flow through; use unknown or a union when it does not. Unnecessary generics add noise without benefit.

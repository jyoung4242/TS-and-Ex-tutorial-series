Introduction

Imagine writing a function that picks the last item from an array. For a number array you write one version. For a string array you write another. For an Actor[] you write a third. The logic is identical every time, but TypeScript does not know that, so you end up copy-pasting. Generics are the escape hatch: write the function once, and let the caller's types flow through it automatically.

Generics are TypeScript's way of saying "I do not know the exact type yet, but whatever it is, I will remember it and keep things consistent." They show up everywhere in the standard library (Array<T>, Promise<T>, Map<K, V>) and throughout ExcaliburJS itself. Understanding them unlocks a large slice of real-world TypeScript code that would otherwise look like alphabet soup.

This lesson focuses on the core idea: type parameters, inference, and when generics are the right tool. You will not need to memorize syntax all at once. Work through the examples slowly, and the pattern will click.

The Problem Generics Solve

Here is the copy-paste trap in action. Without generics, you might write this:


function lastNumber(arr: number[]): number {
  return arr[arr.length - 1];
}

function lastString(arr: string[]): string {
  return arr[arr.length - 1];
}

Same body, different types. The alternative without generics is to reach for any: 


function last(arr: any[]): any {
  return arr[arr.length - 1];
}

const item = last([1, 2, 3]);
// item is typed as `any` — TypeScript has lost track of it
⚠
Warning: any silences the type checker

Using any makes the error go away, but TypeScript stops checking everything downstream. You lose autocomplete, catch fewer bugs, and spread any through your codebase like a leak. Generics give you the flexibility of any without the cost.

Your First Generic Function

A generic function introduces a type parameter in angle brackets right after the function name. By convention, single uppercase letters like T are used, though any name works. 


function last<T>(arr: T[]): T {
  return arr[arr.length - 1];
}

const num = last([10, 20, 30]);     // num: number
const str = last(["a", "b", "c"]); // str: string

Read <T> as "for some type T." When you call last([10, 20, 30]), TypeScript infers that T is number and the return type becomes number automatically. Nothing to annotate at the call site.

💡
Type inference at call sites

You rarely need to write the type argument explicitly. TypeScript infers it from the arguments. Writing last<number>([10, 20, 30]) is valid, but last([10, 20, 30]) is cleaner and equivalent.

Multiple Type Parameters

A function can carry more than one type parameter. A common example is pairing two values of potentially different types:


function pair<A, B>(first: A, second: B): [A, B] {
  return [first, second];
}

const result = pair("score", 9500);
// result: [string, number]

In game code this pattern shows up when you want to bundle an entity with some derived data without losing either type:


import { Actor } from "excalibur";

function tagWith<E, M>(entity: E, metadata: M): { entity: E; meta: M } {
  return { entity, meta: metadata };
}

const actor = new Actor({ name: "Player" });
const tagged = tagWith(actor, { spawnTime: Date.now() });
// tagged.entity: Actor
// tagged.meta: { spawnTime: number }

Generics vs. Union Types

A common question: when should you use a generic instead of a union? The rule of thumb is about relationship. If the input type and output type need to be the same, use a generic. If they can be independent, a union is fine. 


// Union: input and output are loosely related
function describe(value: string | number): string {
  return String(value);
}

// Generic: output type mirrors input type exactly
function identity<T>(value: T): T {
  return value;
}

const n = identity(42);        // n: number (not string | number)
const s = identity("hello");   // s: string
📌
Remember: generics preserve the specific type

If you need the caller to get back the same type they put in (not a widened union), that is the signal to reach for a generic. Unions tell TypeScript "one of these." Generics tell TypeScript "the same one throughout."

Write a Generic Stack

A stack is a last-in, first-out collection. Implement a generic Stack<T> class with three methods.

  1. Define a class Stack<T> with a private items: T[] property initialized to an empty array.
  2. Add a push(item: T): void method that appends to items.
  3. Add a pop(): T | undefined method that removes and returns the last item.
  4. Add a peek(): T | undefined method that returns the last item without removing it.
  5. Instantiate two stacks: a Stack<number> for tracking player scores, and a Stack<string> for tracking visited room names. Push a few values onto each and log the result of pop().

Expected result: TypeScript should infer the correct return type from each stack without any explicit annotations at the call site. Pushing the wrong type (e.g. a string into the number stack) should produce a compile error.

Summary
  • Generics let you write one function or class that works across many types without losing type information the way any does.
  • A type parameter like <T> is a placeholder; TypeScript fills it in at each call site through inference.
  • Multiple type parameters (<A, B>) let you track independent types through the same function.
  • Reach for generics when input and output types need to be the same; use a union when they can vary independently.
  • ExcaliburJS utilities like random pickers, pairing helpers, and generic stacks are natural targets for generic functions.

Introduction

Imagine you are building a game where every entity on screen carries some kind of state: a player carries PlayerState, a projectile carries ProjectileState, an enemy carries EnemyState. Without generics you end up writing nearly identical interfaces three times. With generic interfaces you write the shape once and let the type parameter fill in the difference.

Type aliases do something similar but from a different angle. Where an interface declares a named object shape you can extend and implement, a type alias names any type at all, including unions, intersections, mapped types, and conditional types. Together these two features are the vocabulary you use to describe your whole data model in one place, precisely and without repetition.

This lesson draws a clear line between the two, shows where they overlap, and gives you patterns you can apply immediately in ExcaliburJS scenes, actors, and event systems.

Generic Interfaces

A generic interface is an interface that accepts one or more type parameters. The parameter appears between angle brackets after the interface name and can be used anywhere inside the body. 


// A generic wrapper that describes any successful API response
interface ApiResponse<T> {
  data: T;
  status: number;
  ok: boolean;
}

// Usage: T is now inferred or explicitly set at each call site
const levelResponse: ApiResponse<{ name: string; par: number }> = {
  data: { name: "Ice Cavern", par: 3 },
  status: 200,
  ok: true,
};

console.log(levelResponse.data.name); // "Ice Cavern"

The interface only describes shape. Nothing about it is tied to a specific data type until a consumer provides one. That separation is the whole point.

Extending Generic Interfaces

Generic interfaces participate in inheritance just like concrete interfaces. You can extend them, narrow the type parameter, or introduce new ones. 


interface Entity<TState> {
  id: string;
  state: TState;
  update(delta: number): void;
}

interface PlayerState {
  health: number;
  score: number;
  lives: number;
}

// PlayerEntity extends the generic Entity with a concrete TState
interface PlayerEntity extends Entity<PlayerState> {
  respawn(): void;
}

// A function that works with any Entity regardless of its state shape
function logEntityId<TState>(entity: Entity<TState>): void {
  console.log(`Entity ID: ${entity.id}`);
}
💡
Tip

When you extend a generic interface with a concrete type argument (like Entity<PlayerState>), the resulting interface is fully concrete. Downstream consumers no longer need to supply a type parameter.

Adding Constraints to Type Parameters

You can constrain what types are acceptable as arguments using extends on the parameter itself. This lets the interface body safely access properties that every valid argument is guaranteed to have. 


// Every TState must have at least a `health` property
interface CombatEntity<TState extends { health: number }> {
  id: string;
  state: TState;
  takeDamage(amount: number): void;
}

interface BossState {
  health: number;
  phase: 1 | 2 | 3;
  shieldActive: boolean;
}

// Valid: BossState satisfies the { health: number } constraint
const boss: CombatEntity<BossState> = {
  id: "boss-01",
  state: { health: 500, phase: 1, shieldActive: true },
  takeDamage(amount) {
    this.state.health -= amount;
  },
};
ℹ
Note

Constraints narrow, they do not widen. TState extends { health: number } does not mean every TState is exactly { health: number }. It means every TState has at least a health number property. The concrete type can have additional properties.

Generic Type Aliases

A type alias names a type. When you add a type parameter it becomes a generic type alias: a reusable recipe for constructing a type. Unlike interfaces, type aliases can name primitives, unions, tuples, function signatures, and mapped types. That makes them more flexible but also less extensible. 


// A generic Result type that represents either success or failure
type Result<T, E = Error> = 
  | { ok: true; value: T }
  | { ok: false; error: E };

// Usage
function loadLevel(id: string): Result<Level> {
  if (!levelExists(id)) {
    return { ok: false, error: new Error(`Level ${id} not found`) };
  }
  return { ok: true, value: fetchLevel(id) };
}

const result = loadLevel("world-2");

if (result.ok) {
  console.log(result.value.name); // TypeScript knows .value exists here
} else {
  console.error(result.error.message); // and .error exists here
}

This Result alias cannot be expressed as an interface because it is a union, not a single object shape. That is a situation where a type alias is the only option.

Generic Type Aliases for Function Shapes

Type aliases are particularly useful for naming generic function signatures. This is common in event systems, middleware pipelines, and callback-heavy APIs like ExcaliburJS. 


// A generic event handler type
type Handler<TEvent> = (event: TEvent) = void;

// A registry mapping event names to their handlers
type EventRegistry<TMap extends Record<string, unknown>> = {
  [K in keyof TMap]: Handler<TMap[K]>;
};

// Define your game's event map
interface GameEvents {
  playerDied: { playerId: string; cause: string };
  levelComplete: { levelId: string; timeMs: number };
  enemySpawned: { enemyId: string; position: { x: number; y: number } };
}

// The registry is now fully typed for every event name
const handlers: EventRegistry<GameEvents> = {
  playerDied: ({ playerId, cause }) => {
    console.log(`${playerId} died from ${cause}`);
  },
  levelComplete: ({ levelId, timeMs }) => {
    console.log(`${levelId} cleared in ${timeMs}ms`);
  },
  enemySpawned: ({ enemyId, position }) => {
    console.log(`${enemyId} spawned at (${position.x}, ${position.y})`);
  },
};
💡
Tip

The mapped type [K in keyof TMap]: Handler<TMap[K]> iterates over every key in your event map and produces a typed handler for each one. Add a new event to GameEvents and TypeScript immediately requires a matching handler in the registry. Nothing is left implicit.

Default Type Parameters

Both interfaces and type aliases support default values for type parameters. Defaults let callers omit the parameter when the common case is obvious. 


// The error type defaults to Error if none is supplied
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

// Callers rarely need to override E
type LevelResult = Result<Level>;         // E = Error (default)
type StringResult = Result<string, string>; // E = string (explicit)

// Same pattern works for interfaces
interface Store<TValue, TKey = string> {
  get(key: TKey): TValue | undefined;
  set(key: TKey, value: TValue): void;
}

// Common case: string keys
const assetStore: Store<HTMLImageElement> = { ... };

// Rare case: numeric keys
const chunkStore: Store<MapChunk, number> = { ... };

Interface vs. Type Alias: When to Use Which

Both tools can describe object shapes with type parameters. The meaningful differences appear when you need features that only one of them supports. 


// These two are structurally equivalent for object shapes
interface AssetCache<T> {
  get(key: string): T | undefined;
  set(key: string, asset: T): void;
  has(key: string): boolean;
}

type AssetCacheAlias<T> = {
  get(key: string): T | undefined;
  set(key: string, asset: T): void;
  has(key: string): boolean;
};

For plain object shapes the two are interchangeable. The differences show up in specific scenarios:


// 1. Declaration merging: interfaces support it, type aliases do not
interface Plugin {
  name: string;
}
interface Plugin {
  version: string; // merges with the first declaration
}
// Plugin now has both name and version

// 2. Implementing in a class: interfaces work, type aliases for unions do not
class SoundCache implements AssetCache<AudioBuffer> {
  private store = new Map<string, AudioBuffer>();
  get(key: string) { return this.store.get(key); }
  set(key: string, asset: AudioBuffer) { this.store.set(key, asset); }
  has(key: string) { return this.store.has(key); }
}

// 3. Union types: only type aliases can express them
type SpriteOrAudio = HTMLImageElement | AudioBuffer; // not possible as interface

// 4. Computed / mapped types: only type aliases support them
type Nullable<T> = { [K in keyof T]: T[K] | null };
📌
Remember

Use an interface when describing an object shape that classes may implement or that library consumers might extend. Use a type alias when describing unions, mapped types, tuples, or function signatures, or when you need a name for a type that is not purely an object shape.

⚠
Warning

Declaration merging (the ability to re-open an interface and add properties) is powerful but can be surprising. If you ship a library that exports interfaces, consumers can extend them without your knowledge. If that is not the behavior you want, exporting type aliases prevents accidental merging.

Summary
  • Generic interfaces accept type parameters, letting you describe reusable object shapes without repeating yourself for every concrete type.
  • Generic type aliases can name any type, including unions, tuples, mapped types, and function signatures, making them more flexible than interfaces for non-object shapes.
  • Type parameter constraints (T extends SomeShape) let the interface or alias body safely access properties guaranteed by the constraint.
  • Default type parameters let callers omit the argument when the common case is obvious, keeping call sites clean without losing type precision.
  • Use an interface when you need declaration merging, class implementation, or a shape that library consumers should be able to extend. Use a type alias for everything else.
  • In ExcaliburJS, generic interfaces and type aliases naturally model actor state, asset registries, event payloads, and load results without duplicating code across entity types.

Introduction

Imagine calling a function and not knowing what it expects or what it gives back. You pass in a number, it secretly wanted a string, and the bug only surfaces at 2 AM in production. TypeScript's function type annotations exist to prevent exactly that scenario by making a function's contract visible and machine-checkable right in the source code.

In JavaScript, function signatures are implicit. In TypeScript, you can make them explicit: every parameter can carry a type, and the return value can too. The compiler then enforces that contract for every caller and every implementation, catching whole categories of bugs before you ever run a line of code.

In this lesson you will annotate parameters and return types, learn when to let TypeScript infer and when to be explicit, and get comfortable with void for the common case of functions that do something but return nothing.

Annotating Parameters

A parameter annotation goes right after the parameter name, separated by a colon. TypeScript will reject any call that passes the wrong type, and your editor will show autocomplete and inline error highlighting as you type. 


// Without annotations — TypeScript infers `a` and `b` as `any`
function add(a, b) {
  return a + b;
}

// With annotations — TypeScript knows exactly what is allowed
function add(a: number, b: number) {
  return a + b;
}

add(2, 3);        // OK
add(2, "three");  // Error: Argument of type 'string' is not assignable to parameter of type 'number'
ℹ
Note

When you annotate all parameters, TypeScript can already infer what the function returns in simple cases. You will still often want to annotate the return type explicitly — covered in the next section.

Multiple Parameters and Mixed Types

Each parameter is annotated independently, so a function can accept a mix of types as long as each argument matches its own annotation. 


function formatScore(playerName: string, score: number, isHighScore: boolean): string {
  const tag = isHighScore ? " 🏆" : "";
  return `${playerName}: ${score}${tag}`;
}

formatScore("Ada", 4200, true);   // OK — returns "Ada: 4200 🏆"
formatScore("Ada", "4200", true); // Error: 'string' is not assignable to 'number'

Annotating Return Types

The return type annotation goes after the parameter list, preceded by a colon and before the opening brace. It tells TypeScript (and every reader of the code) what value to expect back. 


function multiply(a: number, b: number): number {
  return a * b;
}

TypeScript can usually infer this on its own. So why annotate it explicitly? There are three strong reasons:

  • Catch mistakes inside the function. If your implementation accidentally returns the wrong type, TypeScript flags it immediately rather than silently widening the inferred type.
  • Document intent. An explicit annotation is a promise to every caller. It survives refactors that might otherwise silently change what gets returned.
  • Improve editor feedback. When callers know the return type up front, autocomplete is more accurate and faster. 

// TypeScript infers the return type as `number | string` — probably not what you want
function getHealth(isDead: boolean) {
  if (isDead) return "dead"; // oops — mixed type slips through
  return 100;
}

// Explicit annotation catches the mistake at the source
function getHealth(isDead: boolean): number {
  if (isDead) return "dead"; // Error: Type 'string' is not assignable to type 'number'
  return 100;
}
💡
Tip

A good rule of thumb: always annotate return types on exported functions and public class methods. For small internal helpers, inference is fine. The key question is whether other code depends on knowing that return type explicitly.

The void Return Type

Many functions perform an action but do not return a meaningful value: logging to the console, updating state, firing a game event. For these, TypeScript provides the void return type. It signals that callers should not rely on any return value from the function. 


function logMessage(message: string): void {
  console.log(`[Game] ${message}`);
  // No return statement needed — void functions implicitly return `undefined`
}

logMessage("Player joined the game"); // OK
const result = logMessage("test");    // `result` is typed as `void` — nearly useless on purpose
⚠
Warning

void and undefined are not the same thing, even though a void function returns undefined at runtime. void means "the caller should ignore this return value." Annotating with undefined would require an explicit return undefined; statement, which is rarely what you want.

void in Callbacks

void appears frequently when you pass functions as callbacks and you do not care what the callback returns. This is common in event systems and game loops. 


// A simple event emitter pattern
function onCollision(handler: (actorName: string) => void): void {
  // Calls `handler` when a collision occurs; ignores any return value
  handler("Enemy");
}

onCollision((name) => {
  console.log(`Collided with ${name}`);
});

Catching Errors Before Runtime

The real payoff of type annotations is that TypeScript surfaces signature mismatches the moment you write the code, not when users run it. Here are the most common errors you will encounter and what they mean. 


function spawnEnemy(x: number, y: number): void {
  console.log(`Spawning enemy at (${x}, ${y})`);
}

// Error 1: Too few arguments
spawnEnemy(10);
// Error: Expected 2 arguments, but got 1.

// Error 2: Wrong type
spawnEnemy(10, "top");
// Error: Argument of type 'string' is not assignable to parameter of type 'number'.

// Error 3: Ignoring a required return value annotation
function getPlayerName(): string {
  return 42;
  // Error: Type 'number' is not assignable to type 'string'.
}
📌
Remember

TypeScript errors are not failures — they are free bug reports. Every red squiggle in your editor is a runtime crash that never happened. Treat them as your first line of testing.

Summary
  • Parameter annotations use the name: type syntax and prevent callers from passing the wrong kind of value.
  • Return type annotations go after the parameter list and make a function's output explicit, catching implementation mistakes at the source.
  • TypeScript can infer return types in simple cases, but annotating explicitly is best practice for exported functions and public APIs.
  • Use void for functions that perform an action and return no meaningful value — it signals to callers that the return value should be ignored.
  • Type errors in function signatures are caught at compile time, before any code runs, making them far cheaper to fix than runtime bugs.

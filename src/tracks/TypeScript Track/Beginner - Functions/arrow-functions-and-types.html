Introduction

You have probably written dozens of arrow functions in JavaScript. They are concise, they handle this lexically, and they read naturally in array methods like .map() and .filter(). But when you move to TypeScript, a question immediately comes up: where do the types go?

Arrow functions in TypeScript follow a straightforward pattern, but there are a handful of places where the syntax trips people up: annotating the variable that holds a function, typing callbacks, and choosing the right return type for functions that return nothing. This lesson walks through all of it with clear, practical examples drawn from game development with ExcaliburJS.

By the end, you will be able to type any arrow function you encounter and understand exactly what TypeScript is inferring behind the scenes.

Arrow Function Syntax Refresher

Before adding types, here is a plain JavaScript arrow function that calculates a sprite's speed from its velocity components:


// JavaScript — no types yet
const getSpeed = (vx, vy) => Math.sqrt(vx * vx + vy * vy);

In TypeScript, you annotate each parameter and, optionally, the return type. The return type annotation goes after the closing parenthesis, before the arrow (=>): 


// TypeScript — explicit parameter and return types
const getSpeed = (vx: number, vy: number): number =>
  Math.sqrt(vx * vx + vy * vy);
ℹ
Note

TypeScript can usually infer the return type from the function body, so the : number after the parentheses is often optional. Being explicit is still recommended for public-facing functions because it documents intent and catches mistakes early.

Multi-Line Arrow Functions

When the body needs multiple statements, wrap it in curly braces and use an explicit return. The type annotation position stays the same: 


const clamp = (value: number, min: number, max: number): number => {
  if (value < min) return min;
  if (value > max) return max;
  return value;
};

// Usage in a game: keep a player's x position inside the screen bounds
const boundedX = clamp(player.pos.x, 0, 800);
💡
Tip

For concise single-expression functions, skip the curly braces and return. TypeScript infers the return type from the expression. Reserve the block body form for functions with logic branches or side effects.

Typing the Variable, Not Just the Parameters

Sometimes you want to declare the type of the function itself on the variable, rather than annotating each parameter inline. This is useful when you are storing a function to be assigned or swapped later: 


// Annotate the variable with a function type
const getSpeed: (vx: number, vy: number) => number =
  (vx, vy) => Math.sqrt(vx * vx + vy * vy);

Notice that when the variable has a full type annotation, TypeScript can infer the parameter types inside the arrow function body, so you do not have to repeat them. This pattern shows up frequently with callbacks: 


// The array type tells TypeScript what each element is,
// so the callback parameter needs no annotation
const speeds: number[] = [
  { vx: 3, vy: 4 },
  { vx: 1, vy: 1 },
  { vx: 0, vy: 5 },
].map((v) => Math.sqrt(v.vx * v.vx + v.vy * v.vy));
//    ^^^  TypeScript already knows this is { vx: number; vy: number }
📌
Remember

Type inference flows from context. If TypeScript knows what type a callback parameter should be (because the array or API tells it), you do not need to annotate the parameter yourself. Let inference do the work.

Functions That Return Nothing: void vs undefined

Game update loops and event handlers often perform side effects and return nothing. TypeScript gives you two options for this, and they are not identical: 


// void: this function is not expected to return a meaningful value
const onPlayerHit = (damage: number): void => {
  player.health -= damage;
  playSoundEffect("hit");
};

// undefined: this function explicitly returns undefined
const getNothing = (): undefined => {
  return undefined;
};

In practice, use void for event handlers and callbacks that do not produce a value. A void-typed function is allowed to return undefined implicitly (by not returning anything), but a function typed as returning undefined must explicitly return undefined.

⚠
Warning

Avoid annotating callbacks with : undefined when you mean : void. Libraries like ExcaliburJS pass callbacks around internally, and a strict undefined return type can cause unexpected type errors when those callbacks are composed together.

Typing Generic-Style Callbacks in Game Code

A common pattern in ExcaliburJS is passing arrow functions to scene event handlers. Here is how to type them correctly:


import { Actor, CollisionStartEvent } from "excalibur";

// Fully typed collision handler arrow function
const onCollision = (evt: CollisionStartEvent): void => {
  const other = evt.other;
  console.log(`Collided with: ${other.name}`);
};

player.on("collisionstart", onCollision);

You can also write this inline. TypeScript infers the event type from the "collisionstart" string literal, so the annotation is optional there: 


// TypeScript infers evt: CollisionStartEvent from the overloaded on() signature
player.on("collisionstart", (evt) => {
  console.log(evt.other.name);
});
💡
Tip

When you hover over an inferred parameter in your editor, you can see exactly what type TypeScript resolved it to. This is a fast way to confirm that inference is working and to discover the correct type name when you need to be explicit.

Avoiding Implicit any in Callbacks

With "strict": true in your tsconfig.json, TypeScript will error if a parameter silently falls back to any. This most often happens when you pass an arrow function to a method TypeScript cannot infer context from: 


// ERROR with strict mode: Parameter 'item' implicitly has an 'any' type
const labels = someUnknownArray.map((item) => item.label);

// FIX: annotate the parameter explicitly
type Labeled = { label: string };
const labels = (someUnknownArray as Labeled[]).map((item: Labeled) => item.label);

// BETTER FIX: type the array at its declaration
const items: Labeled[] = getItems();
const labels = items.map((item) => item.label); // item is inferred as Labeled
📌
Remember

The best place to add type information is at the source, not at the callback. If you type your arrays and variables correctly at declaration, callbacks rarely need explicit parameter annotations.

Try It: Arrow Functions in a Game Loop

The playground below sets up a minimal ExcaliburJS scene. The onPreUpdate handler is an arrow function with typed parameters. Try adding your own typed arrow functions to move the actor or log its position each frame.

import { Engine, Actor, Color, vec } from "excalibur"; const game = new Engine({ width: 600, height: 400 }); const box = new Actor({ x: 300, y: 200, width: 40, height: 40, color: Color.Orange, }); // Typed arrow function: parameters come from Excalibur's update signature const clamp = (value: number, min: number, max: number): number => { if (value < min) return min; if (value > max) return max; return value; }; box.onPreUpdate = (_engine, deltaMs: number): void => { box.vel.x = 60; // pixels per second // Keep the box on screen using our typed clamp arrow function box.pos.x = clamp(box.pos.x, 20, 580); }; game.add(box); game.start();

Summary
  • Parameter types go inside the parentheses (x: number); the return type goes after the closing parenthesis, before the arrow (): number =>).
  • You can annotate the variable holding the function instead of each parameter: const f: (x: number) => number = (x) => x * 2.
  • TypeScript infers callback parameter types from context, such as the element type of the array being mapped. Let it do so rather than repeating annotations unnecessarily.
  • Use void as the return type for event handlers and side-effect functions. Reserve undefined only when the function must explicitly return undefined.
  • With strict mode enabled, TypeScript will catch implicit any in callback parameters. The fix is usually to type the source data structure, not the callback itself.

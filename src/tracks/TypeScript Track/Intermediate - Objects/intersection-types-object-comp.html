Introduction

Imagine you are building an enemy in your game. Some enemies can fly. Some enemies shoot projectiles. Some enemies do both. If you model every combination as a separate interface, your type definitions explode in number and drift out of sync the moment you add a new capability. There has to be a better way to say: "this thing is all of these things at once."

TypeScript's intersection type is exactly that tool. Where a union type (A | B) means "either A or B," an intersection type (A & B) means "both A and B, simultaneously." The result is a single type that requires every property from every member, giving you precise, composable object descriptions without the copy-paste.

In this lesson you will build up from the simplest intersection to a multi-capability game-object pattern that maps directly to how ExcaliburJS actors are structured in real projects.

The Intersection Operator &

An intersection type is written by placing & between two or more types. TypeScript requires any value of that type to satisfy all of the members at once. 

type Position = {
  x: number;
  y: number;
};

type Named = {
  name: string;
};

// A value of type PositionedEntity must have x, y, AND name
type PositionedEntity = Position & Named;

const enemy: PositionedEntity = {
  x: 400,
  y: 200,
  name: "Goblin",
};
ℹ
Note

Intersection types are structural. TypeScript does not care which named type a property came from, only that the combined shape is fully satisfied. PositionedEntity above behaves identically to writing the three properties out manually.

Building Game Objects Through Composition

The real power of intersections shows up when you treat your type definitions as small, focused building blocks and assemble them for each actor type. 

// Focused capability types
type HasHealth = {
  hp: number;
  maxHp: number;
};

type HasDamage = {
  attackPower: number;
  critChance: number;
};

type HasMovement = {
  speed: number;
  isGrounded: boolean;
};

// Compose a full enemy from individual capabilities
type MeleeEnemy = HasHealth & HasDamage & HasMovement & Named;

const orc: MeleeEnemy = {
  name: "Orc Warrior",
  hp: 80,
  maxHp: 80,
  attackPower: 12,
  critChance: 0.1,
  speed: 150,
  isGrounded: true,
};

Now adding a new flying enemy is a matter of defining a HasFlight type and intersecting it in where needed. You never touch the existing pieces. 

type HasFlight = {
  altitude: number;
  maxAltitude: number;
};

// Flying enemy: all of melee enemy's capabilities, plus flight
type FlyingEnemy = MeleeEnemy & HasFlight;

const wyvern: FlyingEnemy = {
  name: "Wyvern",
  hp: 120,
  maxHp: 120,
  attackPower: 18,
  critChance: 0.2,
  speed: 280,
  isGrounded: false,
  altitude: 0,
  maxAltitude: 600,
};
💡
Tip

Keep each building-block type small and single-purpose. A type called HasHealth should only describe health. This makes individual pieces easy to reason about and reusable across many composite types.

Intersection vs. Interface Extension

If you have worked with interface before, you may notice that extending interfaces looks similar on the surface. The two approaches overlap for straightforward cases, but they diverge in important ways. 

// Interface extension approach
interface BaseActor {
  id: string;
}

interface Enemy extends BaseActor {
  hp: number;
}

// Intersection type approach
type BaseActorType = { id: string };
type EnemyType = BaseActorType & { hp: number };

The structural result is the same. The differences become meaningful in three situations:

  • Combining types you do not own. You cannot extend a type alias with an interface in all positions, but you can always intersect any two types with &.
  • Mixing interfaces and type aliases. Intersections work freely across both: SomeInterface & SomeTypeAlias is valid.
  • Conflicting property names. Interface extension raises a compile error when a property is redeclared with a different type. An intersection produces never for that property silently (covered below).
📌
Remember

Prefer interface extension when you are building class hierarchies or want explicit declaration merging. Prefer intersections when you are composing independent capability types, especially across type aliases you cannot reopen.

The Conflicting Property Pitfall

When two types being intersected define the same property with incompatible types, TypeScript resolves the conflict by assigning that property the type never. A never property can never be satisfied, making the whole type effectively unusable for that property. 

type TypeA = {
  id: string;
};

type TypeB = {
  id: number; // conflicts with TypeA.id
};

type Conflict = TypeA & TypeB;

// TypeScript infers: { id: never }
// No value can satisfy both string and number at once.

const bad: Conflict = {
  id: "abc", // Error: Type 'string' is not assignable to type 'never'
};
⚠
Warning

TypeScript does not always immediately surface an error at the point where you write the intersection. The never type may only appear when you try to assign a value. Watch out for intersection types that produce properties typed as never in your editor's hover tooltip, as it is a sign that two members are fighting over the same property.

The fix is to ensure each building-block type owns distinct properties, or to rename conflicting properties before intersecting.

// Before: conflict
type SceneA = { id: string };
type SceneB = { id: number };

// After: disambiguate with descriptive names
type SceneA = { sceneId: string };
type SceneB = { entityId: number };

type SafeComposition = SceneA & SceneB; // { sceneId: string; entityId: number }

Intersection Types with Functions and Methods

Intersection types also compose function signatures. When both sides define the same method, the result is a function that must satisfy both call signatures. This is how TypeScript represents overloaded functions internally. 

type Serializable = {
  serialize(): string;
};

type Updatable = {
  update(delta: number): void;
};

type GameComponent = Serializable & Updatable;

// Any object of type GameComponent must implement both methods
function registerComponent(component: GameComponent): void {
  component.update(16);
  const snapshot = component.serialize();
  console.log("Snapshot:", snapshot);
}

Practical ExcaliburJS Pattern: Composing Actor Traits

In ExcaliburJS, actors carry game logic through their properties and lifecycle methods. Intersection types let you describe exactly which capabilities a function expects without reaching for a monolithic base class. 

import { Actor } from "excalibur";

// Describe only the capabilities this function cares about
type Damageable = {
  hp: number;
  takeDamage(amount: number): void;
};

type Lootable = {
  lootTable: string[];
  dropLoot(): void;
};

// The function signature is self-documenting:
// it requires an Actor that is both damageable AND lootable
function killEnemy(enemy: Actor & Damageable & Lootable): void {
  enemy.takeDamage(enemy.hp); // finish it off
  enemy.dropLoot();
  enemy.kill();
}
ℹ
Note

The concrete actor class still implements these methods at runtime. The intersection type is purely a TypeScript description used to check callers at compile time. No runtime overhead is added.

Summary
  • The & operator creates an intersection type that requires a value to satisfy all member types simultaneously.
  • Intersection types enable capability-based object composition: define small, focused types and combine them only where needed.
  • Intersecting two types with a property of the same name but different types produces never for that property, making it unassignable. Always give conflicting properties distinct names.
  • Intersections work across both type aliases and interface declarations, making them more flexible than interface extension when combining types you do not own.
  • In ExcaliburJS, intersection types let you describe actor capabilities precisely in function signatures without coupling logic to a single class hierarchy.

Introduction

Games are full of dynamic data: a player's inventory keyed by item name, a registry of sound effects keyed by event type, a leaderboard keyed by player ID. In every one of those situations you know the shape of the value but not the exact set of keys at compile time. A plain object literal type like { sword: number; shield: number } won't cut it — you'd have to list every possible key up front.

Index signatures and the Record utility type solve this. They let you tell TypeScript "this object can have any number of keys of type X, and each value will be of type Y" without sacrificing type safety. Once you understand both tools and their trade-offs, you'll reach for the right one instinctively — and avoid the subtle runtime surprise that trips up most developers the first time.

Index Signatures

An index signature describes the type of values that can be stored under any key of a given key type. The syntax places the key in square brackets with a type annotation, followed by a colon and the value type. 


// A general-purpose string-keyed object where every value is a number.
interface StatBlock {
  [stat: string]: number;
}

const enemy: StatBlock = {
  health: 120,
  speed: 45,
  damage: 30,
};

// Reading a key TypeScript has never seen before is still valid.
const armor = enemy["armor"]; // type: number
ℹ
Note

The identifier inside the brackets (stat above) is purely descriptive. TypeScript ignores the name at runtime; it only matters for readability.

Valid Key Types

TypeScript restricts index signature keys to string, number, or symbol. In practice you will use string for named lookups and number for array-like structures. 


// Numeric index: useful for positional data like tile maps.
interface TileRow {
  [column: number]: string; // e.g. "grass" | "water" | "wall"
}

const row: TileRow = ["grass", "grass", "water", "wall"];
const tile = row[2]; // type: string

Mixing Known Keys with an Index Signature

You can combine explicit properties with an index signature, but there is one strict rule: every explicit property's value type must be assignable to the index signature's value type. If the index signature says number, every named property must also be number. 


// Valid — "name" is a string, and the index signature value type is string | number.
interface EntityData {
  name: string;
  [key: string]: string | number;
}

// Invalid — "name" is string, but the index signature says number only.
// TypeScript will flag this with a type error.
interface BrokenEntityData {
  name: string;        // Error: Property 'name' of type 'string' is not assignable
  [key: string]: number; // to string index type 'number'.
}
⚠
Warning

With an index signature in place, TypeScript assumes every key returns a value of the declared type. That means reading a key that was never set returns undefined at runtime, but TypeScript reports the type as number (or whatever you declared). Always check for undefined before using a dynamically read value in production code, or enable the noUncheckedIndexedAccess compiler option to make TypeScript add | undefined automatically.

The Record Utility Type

Record<K, V> is TypeScript's built-in shorthand for an object type whose keys are type K and whose values are type V. Under the hood it is implemented with an index signature, but the surface syntax is often cleaner, especially when the set of keys is a known union rather than string. 


// Equivalent to { [key: string]: number }
type StatBlock = Record;

// More precise: keys must be one of these specific strings.
type ActorType = "player" | "enemy" | "npc" | "projectile";
type SpawnCount = Record;

const spawns: SpawnCount = {
  player:     1,
  enemy:      12,
  npc:        4,
  projectile: 0,
};

// TypeScript will catch a missing or misspelled key.
// spawns.boos = 3; // Error: 'boos' does not exist in type 'SpawnCount'
💡
Tip

Prefer Record<UnionKey, V> over a raw index signature whenever you know the complete set of valid keys. TypeScript will enforce exhaustiveness — if you add a new key to the union, every Record that uses it becomes a compile-time error until you add the new entry. This is exactly the kind of safety net that catches bugs when a game adds a new actor type or item category.

Record vs Index Signature: When to Use Each

Both tools produce similar runtime objects. The choice comes down to what you know about the keys at compile time. 


// Use an index signature when keys are truly open-ended at compile time.
// (e.g., user-defined hotkeys loaded from a config file at runtime)
interface HotkeyMap {
  [action: string]: string; // action name -> key code
}

// Use Record when the key set is fixed and known.
// (e.g., a defined set of game difficulty levels)
type Difficulty = "easy" | "normal" | "hard" | "nightmare";
type DifficultySettings = Record;

const settings: DifficultySettings = {
  easy:      { enemyScale: 0.5, lootScale: 1.5 },
  normal:    { enemyScale: 1.0, lootScale: 1.0 },
  hard:      { enemyScale: 1.5, lootScale: 0.75 },
  nightmare: { enemyScale: 2.5, lootScale: 0.5 },
};
📌
Remember

Index signature when keys are dynamic and open-ended. Record when keys are a known, finite union. Both are safer than using any or casting to object.

Practical Patterns in Game Code

Asset Registry

A common Excalibur pattern is an asset registry that maps resource names to loaded image or sound objects. Using Record with a string union gives you autocomplete and a compile-time guarantee that every asset is accounted for. 


import { ImageSource } from "excalibur";

type SpriteKey =
  | "player-idle"
  | "player-run"
  | "enemy-goblin"
  | "enemy-orc"
  | "tile-grass"
  | "tile-water";

// Every key in SpriteKey must appear — no missing sprites at startup.
const sprites: Record = {
  "player-idle":  new ImageSource("/assets/player-idle.png"),
  "player-run":   new ImageSource("/assets/player-run.png"),
  "enemy-goblin": new ImageSource("/assets/enemy-goblin.png"),
  "enemy-orc":    new ImageSource("/assets/enemy-orc.png"),
  "tile-grass":   new ImageSource("/assets/tile-grass.png"),
  "tile-water":   new ImageSource("/assets/tile-water.png"),
};

function getSprite(key: SpriteKey): ImageSource {
  return sprites[key]; // TypeScript knows this is always ImageSource, not undefined.
}

Dynamic Score Tracker

For data that grows at runtime (player IDs assigned by a server, for instance), an index signature is the right tool because you cannot enumerate all keys ahead of time. 


interface ScoreBoard {
  [playerId: string]: number;
}

const scores: ScoreBoard = {};

function recordScore(playerId: string, points: number): void {
  scores[playerId] = (scores[playerId] ?? 0) + points;
}

recordScore("player-42", 150);
recordScore("player-99", 200);
recordScore("player-42", 50); // now 200

// Guard against a key that was never set.
function getScore(playerId: string): number {
  return scores[playerId] ?? 0;
}
ℹ
Note

The nullish coalescing operator (??) is your best friend when reading from index-signature objects. It handles the undefined case cleanly without treating 0 or "" as falsy.

Try It: Excalibur Playground

The snippet below sets up a minimal Excalibur scene that uses a Record to map actor labels to on-screen colors, and a ScoreBoard index signature to track click counts per actor. Read through the TypeScript, then experiment: add a new actor type to ActorColor and see what TypeScript asks you to fix. 


import { Engine, Actor, Color, vec } from "excalibur";

// Fixed key set — Record enforces exhaustiveness.
type ActorLabel = "hero" | "goblin" | "treasure";

const actorColors: Record = {
  hero:     Color.Blue,
  goblin:   Color.Green,
  treasure: Color.Yellow,
};

// Open-ended key set — index signature handles runtime keys.
interface ClickCounts {
  [label: string]: number;
}

const clicks: ClickCounts = {};

function registerClick(label: string): void {
  clicks[label] = (clicks[label] ?? 0) + 1;
  console.log(`${label} clicked ${clicks[label]} time(s)`);
}

const game = new Engine({ width: 600, height: 400 });

(Object.keys(actorColors) as ActorLabel[]).forEach((label, i) => {
  const actor = new Actor({
    x: 150 + i * 150,
    y: 200,
    width: 60,
    height: 60,
    color: actorColors[label],
  });

  actor.on("pointerdown", () => registerClick(label));
  game.add(actor);
});

game.start();

Build a Loot Table

You are designing the loot system for a dungeon crawler. Each enemy type drops gold at a different rate. Your job is to model this with the right TypeScript tool and write a function that looks up drop amounts safely.

  1. Declare a string union type EnemyType with at least four members: "slime", "goblin", "skeleton", and "dragon".
  2. Create a Record<EnemyType, number> called goldDropTable that maps each enemy type to its gold drop amount.
  3. Write a function getGoldDrop(enemy: EnemyType): number that returns the gold amount for the given enemy.
  4. Now add a second structure using an index signature: a KillLog interface where string keys are enemy IDs (e.g., "goblin-001") and values are { type: EnemyType; goldEarned: number }.
  5. Write a function logKill(id: string, type: EnemyType): void that records the kill in your KillLog, looking up gold from goldDropTable.

🏆 Challenge
Safe Lookup with noUncheckedIndexedAccess

Add "noUncheckedIndexedAccess": true to your tsconfig.json and revisit the KillLog and ScoreBoard patterns from this lesson. TypeScript will now report the value type as T | undefined for every index signature read. Update every read site so the code compiles without non-null assertions (!). Consider writing a generic helper function safeGet<T>(map: Record<string, T>, key: string, fallback: T): T that centralizes the undefined guard and works for any value type.

Summary
  • An index signature ([key: string]: V) types objects with open-ended, runtime-determined keys where values share a common shape.
  • Record<K, V> is a cleaner alternative when the key set is a known, finite union — TypeScript enforces that every key in the union is present.
  • Explicit named properties can coexist with an index signature, but their value types must be assignable to the index signature's value type.
  • Index signatures are optimistic by default: reading an absent key returns undefined at runtime even though TypeScript types it as V. Always guard with ?? or enable noUncheckedIndexedAccess.
  • In Excalibur projects, prefer Record for fixed asset registries and difficulty tables, and index signatures for dynamic runtime data like score boards or kill logs.

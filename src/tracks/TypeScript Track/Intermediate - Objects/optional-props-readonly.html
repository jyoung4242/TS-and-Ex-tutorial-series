  • Use readonly to prevent mutation of object properties after initialization

Introduction

Imagine you are defining a configuration object for a game enemy. Every enemy needs a name and a position, but not every enemy has a boss title, a patrol route, or a custom sprite. Forcing every caller to supply those fields would be tedious and error-prone. TypeScript's optional property modifier (?) solves this elegantly: mark a field as optional, and the type system accepts objects that omit it entirely while still catching typos and wrong types.

On the flip side, some values must never change after an object is created. A player's unique ID, a level's seed, or a physics constant should be locked down. TypeScript's readonly modifier communicates this intent clearly and enforces it at compile time. Together, these two modifiers let you design object shapes that are both flexible where they need to be and rigid where they should be.

Optional Properties with ?

Add a ? after a property name to make it optional. TypeScript will accept objects that omit the field, and the inferred type of that property becomes T | undefined inside the interface. 

interface EnemyConfig {
  name: string;           // required — every enemy needs a name
  health: number;         // required — every enemy needs health
  bossTitle?: string;     // optional — only boss-tier enemies have this
  patrolRadius?: number;  // optional — only patrolling enemies need this
}

// All three of these are valid:
const grunt: EnemyConfig = { name: "Grunt", health: 40 };
const captain: EnemyConfig = { name: "Captain", health: 120, bossTitle: "The Iron Fist" };
const guard: EnemyConfig = { name: "Guard", health: 80, patrolRadius: 200 };
ℹ
Note

Optional properties differ from properties typed as string | undefined. An optional property may be omitted entirely from the object literal. A property typed as string | undefined must still be present in the literal, even if its value is undefined.

Accessing Optional Properties Safely

Because an optional property may be undefined, TypeScript will flag direct use of it where a concrete value is expected. You have two clean options: a narrowing check, or optional chaining with a fallback. 

function announceEnemy(config: EnemyConfig): string {
  // Option 1 — explicit narrowing check
  if (config.bossTitle !== undefined) {
    // TypeScript now knows bossTitle is a string here
    return `${config.bossTitle}: ${config.name} approaches!`;
  }

  return `${config.name} appears!`;
}

function getPatrolRadius(config: EnemyConfig): number {
  // Option 2 — optional chaining with nullish coalescing fallback
  return config.patrolRadius ?? 0;
}
💡
Tip

The ?? (nullish coalescing) operator is a great companion to optional properties. It supplies a default only when the value is null or undefined, so a legitimate falsy value like 0 is preserved. Prefer ?? over || when working with optional numbers or booleans.

Optional Properties in Function Parameters

The same ? syntax works on function parameters, which is especially useful for configuration or options objects passed to utility functions. 

function spawnEnemy(name: string, health: number, bossTitle?: string): void {
  const label = bossTitle ? `[BOSS] ${bossTitle} — ${name}` : name;
  console.log(`Spawning: ${label} (HP: ${health})`);
}

spawnEnemy("Grunt", 40);                         // fine — bossTitle omitted
spawnEnemy("Warlord", 500, "The Undying");       // fine — bossTitle provided
⚠
Warning

Optional parameters must come after all required parameters. Placing an optional parameter before a required one is a compile error. If your options object has many optional fields, prefer an options interface over individual optional parameters to keep signatures readable.

Preventing Mutation with readonly

Prefix any property with readonly and TypeScript will reject any attempt to reassign it after the object is created. This is purely a compile-time constraint — no runtime overhead is added. 

interface PlayerProfile {
  readonly id: string;        // assigned once, never changed
  readonly createdAt: number; // timestamp locked at account creation
  username: string;           // mutable — players can rename themselves
  level: number;              // mutable — level increases over time
}

const player: PlayerProfile = {
  id: "player-001",
  createdAt: Date.now(),
  username: "Archer42",
  level: 1,
};

player.username = "Archer42_Elite"; // OK — username is mutable
player.level = 2;                   // OK — level is mutable

player.id = "player-999";           // Error: Cannot assign to 'id'
                                    // because it is a read-only property.

readonly vs. const

A common source of confusion is when to use const and when to use readonly. The rule is straightforward: const applies to variables, and readonly applies to properties. 

const config = { gravity: 9.8, maxSpeed: 600 };

// const prevents reassigning the variable itself:
// config = { gravity: 0, maxSpeed: 400 }; // Error

// But properties are still mutable!
config.gravity = 0;    // No error — this compiles fine
config.maxSpeed = 999; // No error — this compiles fine

// To lock the properties too, use readonly on the type:
interface PhysicsConfig {
  readonly gravity: number;
  readonly maxSpeed: number;
}

const physics: PhysicsConfig = { gravity: 9.8, maxSpeed: 600 };
physics.gravity = 0; // Error: Cannot assign to 'gravity'
📌
Remember

const locks the binding (what the variable points to). readonly locks the property (what's inside the object). You often need both: const on the variable declaration and readonly on the interface to fully protect a value.

Readonly Arrays

You can also apply readonly semantics to arrays using ReadonlyArray<T> or the shorthand readonly T[]. This prevents methods like push, pop, and direct index assignment from compiling. 

interface LevelConfig {
  readonly name: string;
  readonly spawnPoints: readonly [number, number][]; // array of coordinate pairs
}

const level: LevelConfig = {
  name: "The Forgotten Vault",
  spawnPoints: [[100, 200], [400, 150], [700, 300]],
};

level.spawnPoints.push([900, 100]); // Error: Property 'push' does not exist
                                     // on type 'readonly [number, number][]'
💡
Tip

In ExcaliburJS, actor and scene options objects are excellent candidates for readonly arrays and properties. For example, the list of waypoints in a patrol path should not be modified after the actor is initialized. Marking it readonly makes the intent explicit and prevents accidental mutation in event handlers.

Combining readonly and ?

Both modifiers can appear on the same property. This is common in configuration interfaces where some fields are optional and, once provided, should never be overwritten. 

interface ActorOptions {
  readonly id?: string;          // optional, but immutable if provided
  readonly tag?: string;         // optional label, locked after creation
  x: number;                     // required, mutable (position changes)
  y: number;                     // required, mutable (position changes)
  width?: number;                // optional, mutable (resize is allowed)
  height?: number;               // optional, mutable (resize is allowed)
}

function createActor(options: ActorOptions) {
  const resolvedId = options.id ?? crypto.randomUUID();
  console.log(`Actor created — id: ${resolvedId}, tag: ${options.tag ?? "none"}`);
}

createActor({ x: 100, y: 200 });
createActor({ id: "player", tag: "hero", x: 50, y: 80 });

Notice that readonly id? reads as "this field is optional; if it is present, it cannot be reassigned." The modifiers are orthogonal and compose cleanly.

Try It: Excalibur Playground

The example below models a minimal ExcaliburJS-style setup using optional and readonly properties. A SceneConfig interface locks in the scene name and background color while allowing an optional music track and spawn list. Try adding a new optional field, accessing it safely, and marking a mutable field as readonly to see how the compiler responds. 

// Paste this into the Excalibur playground or any TypeScript sandbox

interface SceneConfig {
  readonly name: string;
  readonly backgroundColor: string;
  musicTrack?: string;
  spawnLimit?: number;
}

function loadScene(config: SceneConfig): void {
  console.log(`Loading scene: ${config.name}`);
  console.log(`Background: ${config.backgroundColor}`);

  if (config.musicTrack !== undefined) {
    console.log(`Playing music: ${config.musicTrack}`);
  }

  const limit = config.spawnLimit ?? 10;
  console.log(`Max spawns: ${limit}`);
}

const dungeonScene: SceneConfig = {
  name: "Sunken Dungeon",
  backgroundColor: "#1a1a2e",
  musicTrack: "dungeon_theme.ogg",
};

const hubScene: SceneConfig = {
  name: "Town Hub",
  backgroundColor: "#2d5a27",
  spawnLimit: 5,
};

loadScene(dungeonScene);
loadScene(hubScene);

// Uncomment to see the readonly error:
// dungeonScene.name = "Renamed"; // Error: Cannot assign to 'name'

Summary
  • The ? modifier makes a property optional, and TypeScript widens its type to include undefined — always narrow or provide a fallback before using it.
  • The readonly modifier prevents reassignment of a property after initialization and applies to both individual fields and arrays.
  • const locks a variable binding; readonly locks an object property. You often need both to fully protect a value from mutation.
  • Optional and readonly modifiers are composable: readonly field?: Type is valid and common in configuration interfaces.
  • Use optional chaining (?.) and nullish coalescing (??) to access optional properties safely and supply meaningful defaults.
  • In game development, readonly is ideal for actor IDs, level names, and physics constants; optional properties shine in flexible configuration objects like scene and actor options.

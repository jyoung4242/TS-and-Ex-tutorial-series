Introduction

Imagine you are building an enemy AI system. An enemy can be idle, chasing the player, or winding up an attack. Each state carries different data: an idle enemy has a patrol radius, a chasing enemy has a target position, and an attacking enemy has a damage value. If you reach for a single interface with a bunch of optional fields, TypeScript cannot tell you which fields are actually present at runtime. You end up writing defensive checks everywhere, and the compiler stays silent even when you forget one.

Discriminated unions solve this cleanly. You model each state as its own type, tag every member with a shared literal property called the discriminant, and then let TypeScript's narrowing do the heavy lifting. When you handle each member in a switch block, the compiler knows exactly which fields are available inside every branch. Forget a branch? The compiler tells you.

This pattern appears constantly in real Excalibur projects: entity state machines, event payloads, scene transition descriptors, and collision result types all benefit from it. By the end of this lesson you will reach for discriminated unions naturally any time a type needs to represent one of several mutually exclusive shapes.

The Problem with Optional Fields

Before looking at the solution, it helps to feel the pain of the alternative. Here is a naive attempt to model enemy state with a single interface: 

// Naive approach — do NOT do this
interface EnemyState {
  kind: string;          // "idle" | "chasing" | "attacking" — but TypeScript doesn't enforce it
  patrolRadius?: number; // only valid when idle
  targetX?: number;      // only valid when chasing
  targetY?: number;      // only valid when chasing
  damage?: number;       // only valid when attacking
}

function handleState(state: EnemyState) {
  if (state.kind === "attacking") {
    // TypeScript thinks state.damage is number | undefined here.
    // We MUST add a null check, but the compiler won't remind us if we forget.
    console.log("Damage:", state.damage!); // forced non-null assertion — a code smell
  }
}

The interface compiles, but it allows nonsensical combinations (an idle enemy with a damage value, for instance). TypeScript cannot help you because it has no way to know which fields belong together.

⚠
Warning

Using ! (non-null assertion) to silence TypeScript is almost always a sign that the type design needs revisiting. It turns off the very safety the type system is offering you.

Building a Discriminated Union

A discriminated union is a type alias that joins several member types with |, where every member shares a property with a unique literal type. That shared property is the discriminant. Here is the enemy state modelled correctly: 

// Each member is its own interface with a literal "kind" discriminant

interface IdleState {
  kind: "idle";
  patrolRadius: number; // required, not optional
}

interface ChasingState {
  kind: "chasing";
  targetX: number;
  targetY: number;
}

interface AttackingState {
  kind: "attacking";
  damage: number;
  windUpMs: number;
}

// The union joins all three
type EnemyState = IdleState | ChasingState | AttackingState;
ℹ
Note

The discriminant property (kind here) must be a literal type on each member, not just string. Literals like "idle" are what allow TypeScript to narrow the union when it sees which value is present.

Narrowing with a Switch Statement

Once you have a discriminated union, narrowing is clean and readable. Inside each case block, TypeScript automatically knows which member you are dealing with, so all of that member's fields become non-optional and fully typed: 

function handleEnemyState(state: EnemyState): void {
  switch (state.kind) {
    case "idle":
      // TypeScript knows state is IdleState here
      console.log(`Patrolling within radius ${state.patrolRadius}m`);
      break;

    case "chasing":
      // TypeScript knows state is ChasingState here
      console.log(`Chasing target at (${state.targetX}, ${state.targetY})`);
      break;

    case "attacking":
      // TypeScript knows state is AttackingState here
      console.log(`Attacking for ${state.damage} damage after ${state.windUpMs}ms wind-up`);
      break;
  }
}

// Usage
const enemy: EnemyState = { kind: "chasing", targetX: 400, targetY: 200 };
handleEnemyState(enemy);
// Output: Chasing target at (400, 200)

No type assertions. No optional-chaining. No if (state.damage !== undefined) guards. TypeScript has narrowed the type for you inside each branch.

💡
Tip

The discriminant property name is a convention, not a keyword. kind, type, tag, and variant are all common choices. Pick one name and use it consistently across your codebase.

Exhaustiveness Checking

One of the biggest wins from discriminated unions is exhaustiveness checking. If you add a new union member later, TypeScript can warn you about every switch statement that forgot to handle it. The pattern uses the never type as a sentinel: 

// A small helper that enforces exhaustiveness
function assertNever(value: never): never {
  throw new Error(`Unhandled union member: ${JSON.stringify(value)}`);
}

function handleEnemyState(state: EnemyState): void {
  switch (state.kind) {
    case "idle":
      console.log(`Patrolling within radius ${state.patrolRadius}m`);
      break;
    case "chasing":
      console.log(`Chasing target at (${state.targetX}, ${state.targetY})`);
      break;
    case "attacking":
      console.log(`Attacking for ${state.damage} damage`);
      break;
    default:
      // If all members are handled above, state has type never here.
      // If you add a new member and forget to handle it, this line
      // will produce a compile-time error on the next line.
      assertNever(state);
  }
}

Now add a new member to the union:

interface StunnedState {
  kind: "stunned";
  durationMs: number;
}

type EnemyState = IdleState | ChasingState | AttackingState | StunnedState;

// TypeScript immediately errors on the assertNever(state) call above:
// Argument of type 'StunnedState' is not assignable to parameter of type 'never'.

The compiler points you directly to every switch statement that needs a new case "stunned" branch. No runtime surprises, no grepping through files.

📌
Remember

never is the bottom type in TypeScript. A value of type never can never actually exist at runtime, which is exactly what makes it useful here. If TypeScript allows code to reach assertNever, it means a case was missed at the type level.

Discriminated Unions in Excalibur

Excalibur's event and collision systems pass data objects that fit naturally into this pattern. Below is a simplified example of how you might type a custom event payload system for your own game logic: 

import { Actor, Engine, CollisionStartEvent } from "excalibur";

// Model different collision outcomes as a discriminated union
interface CoinPickup {
  kind: "coin-pickup";
  value: number;
}

interface EnemyHit {
  kind: "enemy-hit";
  damage: number;
  knockbackX: number;
  knockbackY: number;
}

interface LevelExit {
  kind: "level-exit";
  nextLevel: string;
}

type CollisionOutcome = CoinPickup | EnemyHit | LevelExit;

function resolveCollision(outcome: CollisionOutcome, player: Actor): void {
  switch (outcome.kind) {
    case "coin-pickup":
      // TypeScript knows outcome.value is number
      console.log(`Picked up coin worth ${outcome.value}`);
      break;
    case "enemy-hit":
      // TypeScript knows outcome.damage, outcome.knockbackX, outcome.knockbackY
      player.vel.x = outcome.knockbackX;
      player.vel.y = outcome.knockbackY;
      break;
    case "level-exit":
      // TypeScript knows outcome.nextLevel is string
      console.log(`Transitioning to ${outcome.nextLevel}`);
      break;
    default:
      assertNever(outcome);
  }
}
ℹ
Note

Excalibur's built-in event types like CollisionStartEvent already carry structured data. Discriminated unions are the pattern you reach for when building your own event systems, state machines, or command queues on top of Excalibur.

Try It: Excalibur Playground

The snippet below sets up a minimal Excalibur scene where a player actor cycles through three states: idle, running, and jumping. The state is typed as a discriminated union. Open the playground, paste the code, and watch how TypeScript narrows the type inside each case block. Try adding a falling state and see the compiler flag every unhandled switch branch. 

import { Actor, Engine, Color, vec } from "excalibur";

// --- Discriminated union for player state ---
interface IdleState   { kind: "idle" }
interface RunningState { kind: "running"; velocityX: number }
interface JumpingState { kind: "jumping"; jumpForce: number }

type PlayerState = IdleState | RunningState | JumpingState;

function assertNever(x: never): never {
  throw new Error("Unhandled state: " + JSON.stringify(x));
}

// Applies velocity based on current state
function applyState(player: Actor, state: PlayerState): void {
  switch (state.kind) {
    case "idle":
      player.vel = vec(0, 0);
      player.color = Color.Gray;
      break;
    case "running":
      player.vel = vec(state.velocityX, 0);
      player.color = Color.Green;
      break;
    case "jumping":
      player.vel = vec(0, -state.jumpForce);
      player.color = Color.Blue;
      break;
    default:
      assertNever(state);
  }
}

// --- Excalibur setup ---
const game = new Engine({ width: 800, height: 600 });

const player = new Actor({ x: 400, y: 300, width: 40, height: 40, color: Color.Gray });
game.add(player);

// Cycle through states every 2 seconds
const states: PlayerState[] = [
  { kind: "idle" },
  { kind: "running", velocityX: 120 },
  { kind: "jumping", jumpForce: 300 },
];
let stateIndex = 0;

game.clock.schedule(() => {
  stateIndex = (stateIndex + 1) % states.length;
  applyState(player, states[stateIndex]);
}, 2000, true);

game.start();
applyState(player, states[0]);

Summary
  • A discriminated union is a type that joins several interfaces with |, where each interface carries a shared literal property called the discriminant.
  • TypeScript narrows the union inside a switch (state.kind) block, giving you full type safety for each member's fields without manual guards or assertions.
  • Using optional fields on a single interface to represent mutually exclusive shapes compiles but sacrifices type safety — discriminated unions are the correct model.
  • The assertNever pattern in the default branch turns a runtime concern into a compile-time error, catching any unhandled union member the moment it is added.
  • In Excalibur projects, discriminated unions are the natural fit for entity state machines, custom event payloads, collision outcomes, and scene command systems.

Introduction

Every game is built from objects: a player with a position and health, an enemy with a speed and patrol route, a collectible with a point value and a sound effect. In plain JavaScript these objects are easy to create but easy to break — a typo in a property name, a missing field, a number where a string was expected, and the bug is silent until runtime.

TypeScript fixes this by letting you describe the shape of an object before you use it. Once TypeScript knows what properties an object should have, it checks every place that object is created or passed around and tells you immediately when something is wrong. In this lesson you will learn the main tools for describing object shapes: inline annotations, type aliases, and interface declarations.

You will also see how these patterns show up directly in ExcaliburJS, where almost every engine call accepts a configuration object. Understanding object type annotations makes reading and writing Excalibur code significantly smoother.

Inline Object Type Annotations

The simplest way to annotate an object is inline, right where the variable is declared. The syntax mirrors the object literal itself: property names followed by their types, separated by semicolons inside curly braces. 


// Inline annotation: describe the shape right on the variable
const player: { name: string; health: number; x: number; y: number } = {
  name: "Hero",
  health: 100,
  x: 0,
  y: 0,
};

TypeScript now knows exactly what player looks like. If you try to read a property that was not declared, or assign the wrong type to one that was, you get an error at edit time rather than at runtime. 


// Error: Property 'mana' does not exist on type '{ name: string; health: number; x: number; y: number }'
console.log(player.mana);

// Error: Type 'string' is not assignable to type 'number'
player.health = "full";
ℹ
Note

Inline annotations are fine for one-off objects, but they become hard to read and impossible to reuse as the shape grows. For anything you will use in more than one place, a type alias or interface is the better choice.

Type Aliases for Object Shapes

A type alias gives a name to any type, including object shapes. You write it once and reference it anywhere that shape is needed. 


// Declare the shape once
type Vector2 = {
  x: number;
  y: number;
};

type Actor = {
  name: string;
  position: Vector2;
  speed: number;
};

// Reuse it freely
const enemy: Actor = {
  name: "Goblin",
  position: { x: 200, y: 150 },
  speed: 80,
};

function moveActor(actor: Actor, delta: Vector2): void {
  actor.position.x += delta.x;
  actor.position.y += delta.y;
}

Notice that Vector2 is nested inside Actor. TypeScript checks the entire nested structure, so passing an object with the wrong shape anywhere in the tree is still an error.

💡
Tip

Compose small, focused type aliases into larger ones rather than writing one giant flat object type. Vector2 and Actor are easier to read, test, and reuse separately than a single type with eight properties all at the top level.

Interfaces

An interface is another way to name an object shape. The syntax is slightly different from a type alias, and interfaces have one extra feature: they can be extended and merged, which is useful when building layered systems. 


interface Collidable {
  boundingBoxWidth: number;
  boundingBoxHeight: number;
}

interface Renderable {
  spriteKey: string;
  visible: boolean;
}

// Interfaces can extend one or more other interfaces
interface GameEntity extends Collidable, Renderable {
  id: string;
  position: Vector2;
}

const coin: GameEntity = {
  id: "coin-001",
  position: { x: 400, y: 300 },
  boundingBoxWidth: 16,
  boundingBoxHeight: 16,
  spriteKey: "coin-spin",
  visible: true,
};
ℹ
Note

type aliases can also compose using intersection types (TypeA & TypeB), so the choice between type and interface is often a matter of team convention. A common rule: use interface for public-facing shapes that others might extend, and type for internal or computed shapes.

Structural Typing: Shape Over Name

TypeScript uses structural typing, which means compatibility is determined by the shape of a type, not its name. If an object has all the required properties with the right types, TypeScript considers it compatible, even if it was not explicitly annotated as that type. 


type Positioned = {
  x: number;
  y: number;
};

function printPosition(pos: Positioned): void {
  console.log(`x: ${pos.x}, y: ${pos.y}`);
}

// This object was never declared as Positioned
const turret = { x: 320, y: 240, damage: 50, range: 200 };

// But it is compatible because it has x and y
printPosition(turret); // OK — extra properties are allowed when passing a variable
⚠
Warning

Structural typing has one important exception: excess property checking. When you pass an object literal directly (not through a variable), TypeScript is stricter and will reject extra properties that are not in the expected type. This catches typos in configuration objects. 


// Error: Object literal may only specify known properties,
// and 'damge' does not exist in type 'Positioned'
printPosition({ x: 10, y: 20, damge: 50 });

Object Types in Excalibur

ExcaliburJS uses configuration objects extensively. Nearly every constructor and factory function accepts an options object. Understanding object type annotations lets you read Excalibur's types directly and write correct configuration with full autocomplete support. 


import { Actor, Color, Vector } from "excalibur";

// Excalibur's ActorArgs is an interface with many optional properties.
// You only supply what you need — the rest use engine defaults.
const player = new Actor({
  name: "player",
  pos: new Vector(100, 200),
  width: 32,
  height: 32,
  color: Color.Green,
});

You can also define your own typed configuration objects that wrap or extend Excalibur patterns:


import { Vector } from "excalibur";

type EnemyConfig = {
  readonly id: string;
  spawnPosition: Vector;
  health: number;
  speed: number;
  patrolRadius?: number;
};

function createEnemy(config: EnemyConfig): void {
  const radius = config.patrolRadius ?? 100;
  console.log(
    `Enemy ${config.id} spawned at (${config.spawnPosition.x}, ${config.spawnPosition.y})` +
    ` with patrol radius ${radius}`
  );
}

createEnemy({
  id: "goblin-03",
  spawnPosition: new Vector(640, 360),
  health: 40,
  speed: 90,
});
💡
Tip

In VS Code, hover over any Excalibur constructor or function to see the interface it expects. This is one of the biggest productivity wins from using TypeScript with a well-typed library: the documentation lives right inside your editor.

Summary
  • Inline object annotations describe a shape directly on a variable, but become unwieldy for shapes used in multiple places.
  • type aliases and interface declarations both give reusable names to object shapes; interfaces additionally support extension and declaration merging.
  • TypeScript uses structural typing: an object is compatible with a type if it has at least the required properties with the right types, regardless of where it was declared.
  • Excess property checking applies when object literals are passed directly, catching typos in configuration objects before they become silent runtime bugs.

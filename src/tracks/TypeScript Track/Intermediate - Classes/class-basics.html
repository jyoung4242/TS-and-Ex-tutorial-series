Introduction

When a game grows beyond a few actors, you start repeating the same property bundles everywhere: every enemy has a name, hit points, a speed, and methods like takeDamage and isAlive. Plain objects fall apart here because there is no contract enforcing their shape and no shared place to put the behavior. Classes solve both problems at once.

TypeScript classes build directly on JavaScript classes and add a layer of static type-checking on top. You get typed properties, checked method signatures, and full IDE support including autocomplete and refactoring tools. If you have used object type annotations, most of the ideas here will feel familiar. The difference is that a class produces both a type and a runtime value (the constructor function) at the same time.

In this lesson you will build up a small Enemy class step by step, the same kind of entity you would find inside a real ExcaliburJS game. Every new TypeScript concept is introduced through that single running example so the progression feels concrete rather than academic.

Declaring a Class

A class declaration names the class, lists its properties with their types, and defines a constructor that runs when you call new ClassName(). TypeScript requires every property to either be assigned in the constructor or marked optional with ?. If you forget, the compiler surfaces an error immediately. 

class Enemy {
  name: string;
  hp: number;
  speed: number;

  constructor(name: string, hp: number, speed: number) {
    this.name  = name;
    this.hp    = hp;
    this.speed = speed;
  }
}

const goblin = new Enemy("Goblin", 30, 80);
console.log(goblin.name); // "Goblin"
console.log(goblin.hp);   // 30

TypeScript infers the type of goblin as Enemy automatically. Every property access is checked, and passing the wrong argument type to the constructor is a compile-time error.

ℹ
Note

TypeScript enforces that every declared property is definitely assigned before the constructor exits. If your tsconfig has strictPropertyInitialization: true (the default with strict: true), leaving a property unset is an error, not a silent undefined.

Constructor Parameter Shorthand

Declaring a property and then assigning it in the constructor is repetitive. TypeScript offers a shorthand: prefix a constructor parameter with a keyword like public or readonly and TypeScript declares the property and assigns it for you automatically. 

// Before shorthand (verbose)
class Enemy {
  name: string;
  hp: number;
  speed: number;

  constructor(name: string, hp: number, speed: number) {
    this.name  = name;
    this.hp    = hp;
    this.speed = speed;
  }
}

// After shorthand (concise, identical behavior)
class Enemy {
  constructor(
    public name: string,
    public hp: number,
    public speed: number,
  ) {}

  takeDamage(amount: number): void {
    this.hp -= amount;
  }

  isAlive(): boolean {
    return this.hp > 0;
  }
}

Both versions compile to the same JavaScript. The shorthand is the style you will see in most TypeScript codebases and throughout ExcaliburJS source code, so it is worth getting comfortable with it early.

ℹ
Coming Up: Access Modifiers

You will notice keywords like public, private, and readonly on class properties throughout TypeScript codebases. These control visibility and mutability and are covered in depth in the next module. For now, using public on shorthand parameters is enough to make the syntax work.

📌
Remember

The shorthand only works in the constructor. Placing a visibility keyword on any other method parameter is a syntax error.

Methods and this

Methods are functions defined inside the class body. Inside a method, this refers to the instance the method was called on. TypeScript knows the type of this automatically from the class definition, so all property accesses through this are checked. 

class Enemy {
  constructor(
    public  name: string,
    private hp: number,
    private maxHp: number,
  ) {}

  takeDamage(amount: number): void {
    this.hp = Math.max(0, this.hp - amount);
  }

  heal(amount: number): void {
    this.hp = Math.min(this.maxHp, this.hp + amount);
  }

  isAlive(): boolean {
    return this.hp > 0;
  }

  // Returning 'this' enables method chaining
  describe(): string {
    return `${this.name} — ${this.hp}/${this.maxHp} HP`;
  }
}

const troll = new Enemy("Troll", 100, 100);
troll.takeDamage(40);
troll.heal(10);
console.log(troll.describe()); // "Troll — 70/100 HP"
console.log(troll.isAlive());  // true
ℹ
Note

Arrow functions stored as class fields (method = () => {}) always bind this lexically. Regular methods do not. In game code you often pass methods as callbacks, and in those cases an arrow field is safer. You will explore this tradeoff in the Higher-Order Functions lesson.

Classes in a Game Context

ExcaliburJS actors are themselves classes. When you extend ex.Actor you are already using class inheritance. But before reaching for full Excalibur actors, it is common to model pure game-data entities (enemies, items, save-state records) as plain TypeScript classes that carry no rendering logic. These are easy to test and easy to serialize. 

import * as ex from "excalibur";

// A pure data class — no Excalibur dependency
class EnemyStats {
  constructor(
    public  readonly name: string,
    private hp: number,
    public  readonly speed: number,
    public  readonly scoreValue: number,
  ) {}

  takeDamage(amount: number): void {
    this.hp = Math.max(0, this.hp - amount);
  }

  isAlive(): boolean {
    return this.hp > 0;
  }
}

// An Excalibur actor that owns the stats object
class EnemyActor extends ex.Actor {
  private stats: EnemyStats;

  constructor(stats: EnemyStats, pos: ex.Vector) {
    super({ pos, width: 32, height: 32 });
    this.stats = stats;
  }

  onPreUpdate(_engine: ex.Engine, _delta: number): void {
    if (!this.stats.isAlive()) {
      this.kill();
    }
  }

  hit(damage: number): void {
    this.stats.takeDamage(damage);
  }
}

// Usage
const goblinStats = new EnemyStats("Goblin", 30, 80, 50);
const goblin = new EnemyActor(goblinStats, ex.vec(200, 300));

Separating the stats model from the visual actor is a common pattern in game development. It lets you unit-test damage logic without needing an Excalibur engine instance, and it keeps each class focused on a single responsibility.

Summary
  • A TypeScript class declares typed properties, a constructor, and methods in one block, giving you both a runtime value and a compile-time type.
  • Constructor parameter shorthand (prefixing a parameter with a keyword like public) declares and assigns a property in a single step, eliminating repetitive boilerplate.
  • TypeScript knows the type of this inside class methods automatically, so all property and method accesses are statically checked.
  • Separating pure data classes from ExcaliburJS actor classes keeps game logic testable and each class focused on a single responsibility.
  • Access modifiers like private and readonly control visibility and mutability — covered in depth in the Access Modifiers module.

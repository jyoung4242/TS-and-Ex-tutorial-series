Introduction

Imagine you are building a game with several enemy types: a Goblin, a Skeleton, and a Dragon. All of them need an update() loop, a takeDamage() method, and a die() animation. The logic for takeDamage() is the same for every enemy, but die() looks completely different per enemy type. How do you share the common code without accidentally letting someone instantiate a bare "Enemy" with no visual or behavior?

Abstract classes solve this precisely. They let you write shared logic once in a base class, mark the parts that every subclass must define as abstract, and then have TypeScript enforce that no one ever creates a raw instance of the base. You get inheritance and enforcement in a single construct.

Declaring an Abstract Class

Prefix the class keyword with abstract. That is the only syntactic change. The class can now contain both regular members with full implementations and abstract members that have no body. 

abstract class Enemy {
  name: string;
  health: number;

  constructor(name: string, health: number) {
    this.name = name;
    this.health = health;
  }

  // Concrete method: shared logic lives here once.
  takeDamage(amount: number): void {
    this.health -= amount;
    console.log(`${this.name} takes ${amount} damage. HP: ${this.health}`);
    if (this.health <= 0) {
      this.die();
    }
  }

  // Abstract method: every subclass must provide its own version.
  abstract die(): void;
}
ℹ
Note

Abstract methods have no curly-brace body at all. They end with a semicolon after the signature. Adding a body is a TypeScript compiler error.

Why You Cannot Instantiate an Abstract Class

TypeScript will refuse to compile code that calls new on an abstract class. This is intentional: an abstract class is a blueprint, not a finished product. 

// Error: Cannot create an instance of an abstract class.
const e = new Enemy("Generic Enemy", 100);

This protects you from creating an object that has an unfulfilled die() contract. You must subclass first.

📌
Remember

Abstract classes exist to be extended, never to be instantiated directly. TypeScript enforces this at compile time, not at runtime.

Implementing a Concrete Subclass

A subclass uses extends exactly as with any class. The only new requirement is that it must implement every abstract method declared in the parent, or TypeScript will report an error listing every missing implementation. 

class Goblin extends Enemy {
  constructor() {
    super("Goblin", 30);
  }

  // Required: fulfills the abstract contract.
  die(): void {
    console.log(`${this.name} squeals and vanishes in a puff of green smoke.`);
  }
}

class Dragon extends Enemy {
  constructor() {
    super("Dragon", 500);
  }

  die(): void {
    console.log(`${this.name} lets out a final roar and crumbles to ash.`);
  }
}

// Both are valid because all abstract methods are implemented.
const goblin = new Goblin();
const dragon = new Dragon();

goblin.takeDamage(35); // Logs damage, then calls Goblin.die()
dragon.takeDamage(10); // Only logs damage; Dragon survives

Notice that takeDamage() is inherited as-is. The subclasses do not repeat that logic. Only the parts that genuinely differ per type live in the subclass.

Abstract Properties

You can mark properties as abstract too, not just methods. This forces subclasses to declare the property and give it a concrete type or value. 

abstract class Enemy {
  abstract readonly spriteKey: string; // Subclass must declare this.
  abstract name: string;
  abstract health: number;

  takeDamage(amount: number): void {
    this.health -= amount;
  }

  abstract die(): void;
}

class Skeleton extends Enemy {
  readonly spriteKey = "skeleton-sprite";
  name = "Skeleton";
  health = 50;

  die(): void {
    console.log(`${this.name} collapses into a pile of bones.`);
  }
}
💡
Tip

Abstract properties work well for values that are constant per subclass but differ between types, such as a sprite key, a display name, or a point value. You declare the contract once and each subclass fills in its own literal.

What About Interfaces?

You may already be wondering how abstract classes relate to interfaces. Both can declare method signatures that a type must implement, so the choice between them is a real design decision worth thinking about carefully.

Using Abstract Classes as Type Annotations

Even though you cannot instantiate an abstract class, you can use it as a type. This is powerful: you can write functions that accept any concrete subclass and call the shared methods without knowing which subclass it is. 

function simulateCombat(enemy: Enemy, incomingDamage: number): void {
  console.log(`Attacking ${enemy.name}...`);
  enemy.takeDamage(incomingDamage);
}

// Both calls work because Goblin and Dragon both extend Enemy.
simulateCombat(new Goblin(), 35);
simulateCombat(new Dragon(), 10);

The parameter type Enemy tells TypeScript "any object whose class extends Enemy." This is structural polymorphism backed by the abstract class contract.

ℹ
Note

This pattern is especially useful in game loops. A scene can hold an Enemy[] array and call enemy.update() on every entry without caring which concrete type each one is.

Summary
  • The abstract keyword on a class prevents direct instantiation and signals that the class is a shared blueprint, not a finished object.
  • Abstract methods declare a required signature with no body; every concrete subclass must implement them or TypeScript will report an error.
  • Abstract classes can hold real, reusable implementation alongside abstract contracts, which is the key advantage over interfaces.
  • You can use an abstract class as a type annotation to write functions that accept any valid subclass, enabling polymorphism across a whole family of types.
  • In ExcaliburJS, abstract classes are a natural fit for actor hierarchies: write the game-loop plumbing once and let each concrete actor type define its own visual and behavioral responses.

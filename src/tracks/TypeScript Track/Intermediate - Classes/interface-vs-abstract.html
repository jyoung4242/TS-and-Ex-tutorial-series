Introduction

You are building a game. You have Player, Enemy, and Collectible all needing a update() method. You want TypeScript to enforce that contract everywhere it matters. You reach for... what exactly? An interface? An abstract class? Both?

Interfaces and abstract classes look similar on the surface: both let you define a shape that other types must satisfy, and both prevent direct instantiation of that shape alone. But they work very differently at runtime, they signal different design intentions, and picking the wrong one causes real pain later. This lesson draws a sharp line between them so you always know which tool to reach for.

The examples here are grounded in ExcaliburJS, where the interface vs abstract class decision comes up constantly when building actor hierarchies and component systems.

Interfaces: Pure Contracts

An interface is a compile-time-only contract. It describes a shape: the names and types of properties and methods an object must have. It produces zero JavaScript output. There is nothing at runtime. 


interface Updatable {
  update(elapsedMs: number): void;
}

interface Drawable {
  draw(ctx: CanvasRenderingContext2D): void;
}

Any class that implements an interface must provide a concrete body for every member declared in that interface. TypeScript enforces this at compile time. 


class Bullet implements Updatable, Drawable {
  private x: number = 0;

  update(elapsedMs: number): void {
    this.x += 10 * (elapsedMs / 1000);
  }

  draw(ctx: CanvasRenderingContext2D): void {
    ctx.fillRect(this.x, 100, 4, 10);
  }
}
ℹ
Note

A class can implement as many interfaces as you like. This is the primary way to compose contracts in TypeScript without building deep inheritance chains.

Interfaces describe capability, not origin

Because interfaces only describe a shape, completely unrelated classes can satisfy the same interface. A UIButton and a PlayerSprite could both implement Drawable without sharing any inheritance relationship. This is structural typing in action. 


function renderAll(items: Drawable[], ctx: CanvasRenderingContext2D): void {
  for (const item of items) {
    item.draw(ctx);
  }
}

// Both work here even though they share no base class:
renderAll([new Bullet(), new UIButton()], ctx);
💡
Tip

Use an interface when you want to describe a capability that many unrelated types might share, or when you need a class to satisfy multiple independent contracts.

Abstract Classes: Partial Blueprints

An abstract class sits between a fully concrete class and an interface. It can contain real, runnable implementation that subclasses automatically inherit, but it can also declare abstract methods that subclasses must override. You cannot instantiate an abstract class directly. 


abstract class GameActor {
  protected x: number;
  protected y: number;

  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }

  // Concrete method: shared by every subclass automatically
  moveTo(x: number, y: number): void {
    this.x = x;
    this.y = y;
  }

  // Abstract method: every subclass MUST implement this
  abstract update(elapsedMs: number): void;
}

Now a concrete subclass fills in the abstract gap:


class Enemy extends GameActor {
  private speed = 80;

  // TypeScript error if this is missing -- abstract method not implemented
  update(elapsedMs: number): void {
    this.x += this.speed * (elapsedMs / 1000);
  }
}

const e = new Enemy(0, 0);
e.moveTo(100, 200); // inherited from GameActor
e.update(16);       // defined on Enemy
⚠
Warning

You cannot do new GameActor(0, 0). TypeScript will refuse with "Cannot create an instance of an abstract class." This is intentional: abstract classes are blueprints, not finished objects.

Two things only abstract classes can do

Interfaces are compile-time only, which means they have two hard limits. Abstract classes have neither:

  1. Shared implementation. An abstract class can provide real method bodies that every subclass inherits without repeating code. An interface cannot provide any implementation at all.
  2. State (fields and a constructor). An abstract class can declare instance fields and initialize them in a constructor. An interface describes the shape of those fields but cannot own or initialize them. 

abstract class GameActor {
  // Fields: only possible in a class
  protected health: number;
  protected name: string;

  constructor(name: string, health: number) {
    this.name = name;
    this.health = health;
  }

  // Concrete shared logic
  isAlive(): boolean {
    return this.health > 0;
  }

  takeDamage(amount: number): void {
    this.health = Math.max(0, this.health - amount);
  }

  // Subclasses supply this
  abstract update(elapsedMs: number): void;
}
📌
Remember

Abstract classes exist in the compiled JavaScript output as real classes. Interfaces are erased entirely. If you need shared logic or initialized state, you need an abstract class. If you only need a contract with no shared logic, an interface is lighter and more flexible.

Comparing Them Side by Side

Here is the same design expressed both ways so you can feel the difference:

As an interface


interface Damageable {
  health: number;
  takeDamage(amount: number): void;
  isAlive(): boolean;
}

class Slime implements Damageable {
  health = 30;

  takeDamage(amount: number): void {
    this.health = Math.max(0, this.health - amount);
  }

  isAlive(): boolean {
    return this.health > 0;
  }
}

class Tower implements Damageable {
  health = 200;

  takeDamage(amount: number): void {
    this.health = Math.max(0, this.health - amount);
  }

  // Every class must copy this logic -- no sharing
  isAlive(): boolean {
    return this.health > 0;
  }
}

As an abstract class


abstract class Damageable {
  protected health: number;

  constructor(health: number) {
    this.health = health;
  }

  takeDamage(amount: number): void {
    this.health = Math.max(0, this.health - amount);
  }

  isAlive(): boolean {
    return this.health > 0;
  }

  abstract update(elapsedMs: number): void;
}

class Slime extends Damageable {
  constructor() {
    super(30);
  }
  update(elapsedMs: number): void { /* slime logic */ }
}

class Tower extends Damageable {
  constructor() {
    super(200);
  }
  update(elapsedMs: number): void { /* tower logic */ }
}

In the abstract class version, takeDamage and isAlive are written once and inherited everywhere. The interface version forces every implementor to repeat them. When that shared logic needs to change, the abstract class makes it a one-line fix.

Combining Both: The Common Pattern

In real projects you often use both. An abstract base class provides shared state and logic across a family of related types, while interfaces layer in additional contracts that span unrelated families. 


// A pure capability contract -- no implementation
interface Serializable {
  serialize(): string;
  deserialize(data: string): void;
}

// A family base with shared logic
abstract class GameActor {
  protected health: number;
  constructor(health: number) { this.health = health; }
  isAlive(): boolean { return this.health > 0; }
  abstract update(elapsedMs: number): void;
}

// A concrete class that belongs to the family AND satisfies the capability
class Player extends GameActor implements Serializable {
  private name: string;

  constructor(name: string) {
    super(100);
    this.name = name;
  }

  update(elapsedMs: number): void {
    // player movement logic
  }

  serialize(): string {
    return JSON.stringify({ name: this.name, health: this.health });
  }

  deserialize(data: string): void {
    const parsed = JSON.parse(data);
    this.name = parsed.name;
    this.health = parsed.health;
  }
}
💡
Tip

Think of it this way: abstract classes express what a thing is (an Actor, a Component, a Scene). Interfaces express what a thing can do (Serializable, Drawable, Updatable). Using both together is not duplication; it is expressive design.

How to Decide

When you are staring at a blank file wondering which to reach for, work through these questions in order:

  1. Do I need shared implementation or initialized state? Yes: abstract class. No: keep reading.
  2. Is this a contract that unrelated types might need to satisfy? Yes: interface. No: keep reading.
  3. Am I building a family of related types that share an identity? Yes: abstract class.
  4. Do I need a type to satisfy multiple independent contracts? Yes: interfaces (a class can only extend one base, but can implement many interfaces).
⚠
Warning

TypeScript classes support single inheritance only. If you make everything an abstract class and a new class needs to inherit from two of them, you are stuck. Interfaces are composable; inheritance chains are not. Favor interfaces for contracts, abstract classes only when shared implementation or state genuinely justifies it.

Summary
  • Interfaces are compile-time-only contracts that describe a shape; they produce no JavaScript output and cannot contain implementation or state.
  • Abstract classes are real classes that cannot be instantiated directly; they can provide shared method bodies and initialized fields that subclasses inherit.
  • A class can implement multiple interfaces but can only extend one abstract class; favor interfaces for cross-cutting capabilities and abstract classes for related families that share logic.
  • The two things only abstract classes can do: hold shared implementation and own initialized state via a constructor.
  • The two constructs work best together: use abstract classes to express what a type is, and interfaces to express what a type can do.

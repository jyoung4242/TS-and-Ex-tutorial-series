Introduction

Imagine you have a dozen different enemy classes in your game. Each one needs logging when it is created, validation that its health value is positive, and a tag that marks it as an Enemy for the collision system. You could copy that boilerplate into every class, but the moment a requirement changes you are editing a dozen files. Decorators let you write that logic once, attach it with a single line, and move on.

A decorator is a function that receives information about a class, method, property, or parameter at definition time and can read or modify it. TypeScript adopted the decorator proposal from JavaScript, so you will see decorators used heavily in frameworks like Angular, NestJS, and TypeORM. They are also a great fit for game code where behavior patterns repeat across many entity types.

ℹ
Compiler flag required

Decorators are a stage-3 JavaScript proposal. To use them in TypeScript you must enable "experimentalDecorators": true in your tsconfig.json. If you also want decorator metadata (for dependency injection patterns), add "emitDecoratorMetadata": true. Without the flag the compiler will refuse to compile decorator syntax.

Class Decorators

A class decorator is applied to the constructor of a class. It receives the constructor as its only argument. You can use it to inspect the class, add static properties, or wrap the constructor entirely. 


// The simplest possible class decorator: it receives the class constructor.
function Loggable(constructor: Function) {
  console.log(`Class defined: ${constructor.name}`);
}

@Loggable
class Player {
  name: string;
  constructor(name: string) {
    this.name = name;
  }
}

// Console output at class-definition time (not at instantiation time):
// "Class defined: Player"

Notice the decorator runs when the class is defined, not when it is instantiated. That makes class decorators ideal for registration or metadata tasks.

Returning a new constructor

If your class decorator returns a value, TypeScript expects it to be a constructor that extends the original class. This is how you wrap or augment the class itself. 


// A decorator that seals the class so no new properties can be added to instances.
function Sealed(constructor: Function) {
  Object.seal(constructor);
  Object.seal(constructor.prototype);
}

// A decorator factory that stamps a tag onto every instance.
function Tagged(tag: string) {
  return function (Base: T) {
    return class extends Base {
      entityTag = tag;
    };
  };
}

@Tagged("enemy")
class Goblin {
  health = 30;
}

const g = new Goblin();
console.log((g as any).entityTag); // "enemy"
💡
Decorator factories give you parameters

@Tagged("enemy") is a decorator factory: a function that returns a decorator. Use this pattern whenever you need to pass configuration to a decorator. The outer function captures the argument; the inner function is the actual decorator.

Method Decorators

A method decorator is placed just before a method definition. It receives three arguments: the prototype of the class (or the constructor for static methods), the method name as a string, and the property descriptor for that method. 


// Signature of a method decorator
function MyDecorator(
  target: Object,           // prototype (or constructor for static)
  propertyKey: string,      // method name
  descriptor: PropertyDescriptor
): PropertyDescriptor | void {
  // descriptor.value is the original method function
}

The most common use is to wrap descriptor.value with your own function, then return the modified descriptor. 


// Log every call to a method, including arguments and return value.
function LogCall(
  target: Object,
  propertyKey: string,
  descriptor: PropertyDescriptor
): PropertyDescriptor {
  const original = descriptor.value as Function;

  descriptor.value = function (...args: unknown[]) {
    console.log(`[${propertyKey}] called with`, args);
    const result = original.apply(this, args);
    console.log(`[${propertyKey}] returned`, result);
    return result;
  };

  return descriptor;
}

class Enemy {
  health = 50;

  @LogCall
  takeDamage(amount: number): number {
    this.health -= amount;
    return this.health;
  }
}

const spider = new Enemy();
spider.takeDamage(10);
// [takeDamage] called with [10]
// [takeDamage] returned 40
⚠
Arrow functions and decorators do not mix

If you define a method as a class field arrow function (takeDamage = () => {}), a method decorator cannot intercept it. Arrow function class fields are instance properties, not prototype methods, so the decorator has no descriptor to wrap. Stick to regular method syntax when you want decorators to work.

Property Decorators

A property decorator fires on a class property declaration. It receives the prototype and the property key, but not a descriptor, because properties do not have descriptors at class definition time. You commonly use property decorators to record metadata or define a getter/setter on the prototype. 


// Validate that a numeric property is always positive.
function Positive(target: Object, propertyKey: string) {
  let value: number;

  Object.defineProperty(target, propertyKey, {
    get() {
      return value;
    },
    set(incoming: number) {
      if (incoming < 0) {
        throw new RangeError(`${propertyKey} must be positive, got ${incoming}`);
      }
      value = incoming;
    },
    enumerable: true,
    configurable: true,
  });
}

class Actor {
  @Positive
  health!: number;
}

const actor = new Actor();
actor.health = 100;   // fine
actor.health = -5;    // throws: "health must be positive, got -5"
ℹ
The definite assignment assertion

The ! after health tells TypeScript "I promise this will be assigned before use." Without it, the compiler complains that a decorated property may be undefined, because it cannot follow the Object.defineProperty logic inside the decorator.

Parameter Decorators

A parameter decorator is placed just before a parameter in a constructor or method signature. It receives the prototype, the method name (or undefined for constructor parameters), and the zero-based index of the parameter. 


// Mark a parameter's index in metadata so an injection system can read it later.
const INJECTED_PARAMS = new Map();

function Inject(target: Object, _methodKey: string | symbol, paramIndex: number) {
  const ctor = target as Function;
  const existing = INJECTED_PARAMS.get(ctor) ?? [];
  existing.push(paramIndex);
  INJECTED_PARAMS.set(ctor, existing);
}

class Scene {
  constructor(@Inject public renderer: unknown) {}
}

console.log(INJECTED_PARAMS.get(Scene)); // [0]
💡
Parameter decorators are rarely standalone

On their own, parameter decorators can only record information. They are designed to be paired with a class or method decorator that reads that information and acts on it. This two-decorator pattern is the foundation of dependency injection in frameworks like Angular and NestJS.

Composing Multiple Decorators

You can stack decorators on a single target. The important thing to know is that decorator factories (the outer calls) evaluate top to bottom, but the returned decorator functions apply bottom to top. Think of it like function composition: f(g(x)). 


function First() {
  console.log("First factory evaluated");
  return function (_target: Object, _key: string, descriptor: PropertyDescriptor) {
    console.log("First decorator applied");
    return descriptor;
  };
}

function Second() {
  console.log("Second factory evaluated");
  return function (_target: Object, _key: string, descriptor: PropertyDescriptor) {
    console.log("Second decorator applied");
    return descriptor;
  };
}

class Demo {
  @First()
  @Second()
  doSomething() {}
}

// Output:
// First factory evaluated
// Second factory evaluated
// Second decorator applied
// First decorator applied
📌
Evaluation vs. application order

Factories evaluate top to bottom. Decorators apply bottom to top. The decorator closest to the method runs first; the one farthest away runs last. Keep this in mind when order matters, such as when one decorator depends on the output of another.

Decorators in ExcaliburJS Game Code

ExcaliburJS entities are plain TypeScript classes, so decorators slot in naturally. Below is a practical pattern: a @RegisterEntity decorator that adds a class to a game-wide registry at definition time, and a @Clamp property decorator that keeps a health value inside a safe range. 


import { Actor, Color, Engine } from "excalibur";

// ── Registry ────────────────────────────────────────────────────────────────
const entityRegistry = new Map();

function RegisterEntity(name: string) {
  return function (constructor: typeof Actor) {
    entityRegistry.set(name, constructor);
    console.log(`Registered entity: ${name}`);
  };
}

// ── Clamped property ─────────────────────────────────────────────────────────
function Clamp(min: number, max: number) {
  return function (target: Object, propertyKey: string) {
    let value = 0;
    Object.defineProperty(target, propertyKey, {
      get() { return value; },
      set(incoming: number) {
        value = Math.min(max, Math.max(min, incoming));
      },
      enumerable: true,
      configurable: true,
    });
  };
}

// ── Method: log whenever the actor takes damage ──────────────────────────────
function LogDamage(
  _target: Object,
  _key: string,
  descriptor: PropertyDescriptor
): PropertyDescriptor {
  const original = descriptor.value as (amount: number) => void;
  descriptor.value = function (amount: number) {
    console.log(`${this.constructor.name} takes ${amount} damage`);
    original.call(this, amount);
  };
  return descriptor;
}

// ── Entity definition ────────────────────────────────────────────────────────
@RegisterEntity("Skeleton")
class Skeleton extends Actor {
  @Clamp(0, 100)
  health!: number;

  constructor() {
    super({ color: Color.fromHex("#888"), width: 32, height: 48 });
    this.health = 80;
  }

  @LogDamage
  takeDamage(amount: number) {
    this.health -= amount;
    if (this.health === 0) {
      this.kill();
    }
  }
}

// const SkeletonClass = entityRegistry.get("Skeleton")!;
// const enemy = new SkeletonClass();
// scene.add(enemy);

Decorators shine in large entity hierarchies

When you have many entity classes (bosses, projectiles, pickups, traps), a shared decorator library means each class stays focused on its own behavior. Cross-cutting concerns like logging, registration, and validation live in one place and are added with a single line.

Summary
  • Decorators are functions applied to classes, methods, properties, or parameters at class definition time using the @ syntax.
  • Enable decorators with "experimentalDecorators": true in tsconfig.json.
  • Class decorators receive the constructor; method decorators receive the prototype, key, and property descriptor; property decorators receive the prototype and key; parameter decorators receive the prototype, key, and parameter index.
  • Decorator factories (@Tagged("enemy")) are functions that return decorators, giving you a way to pass configuration into a decorator.
  • When stacking decorators, factories evaluate top to bottom but the decorator functions apply bottom to top.
  • In ExcaliburJS, decorators are a clean way to add registration, validation, and logging to entity classes without cluttering each class's own logic.

Introduction

Imagine you have an array of game entities: some are Player objects, some are Enemy objects, and some might be null placeholders left behind after entities were removed. You want to filter the array down to only the live enemies before running collision logic. You call .filter(), but TypeScript still thinks the result contains null. Why?

The problem is that .filter() accepts a predicate that returns boolean, and TypeScript does not automatically narrow the array element type based on what a plain boolean tells it. To close this gap, TypeScript provides type predicates: a special function return annotation that says "if this function returns true, the argument is this specific type." This lesson covers exactly how to write and use them.

You will see this pattern constantly in real codebases: filtering nullable values out of arrays, separating a union into typed buckets, and tagging entity collections in game loops. Getting comfortable with it now will make working with arrays of mixed types feel natural.

What Is a Type Predicate?

A type predicate is a return type annotation on a function that takes the form parameterName is SomeType. When TypeScript sees this annotation it treats the function as a type guard: inside any branch where the function returned true, TypeScript narrows the type of the checked variable to SomeType. 


// A plain boolean guard — TypeScript does NOT narrow based on this
function isStringPlain(value: unknown): boolean {
  return typeof value === "string";
}

// A type predicate — TypeScript DOES narrow based on this
function isString(value: unknown): value is string {
  return typeof value === "string";
}

const input: unknown = "hello";

if (isString(input)) {
  // TypeScript knows input is string here
  console.log(input.toUpperCase()); // OK
}
ℹ
Note

The value is Type syntax only appears in the return type position. The function body still returns a regular boolean at runtime. TypeScript uses the annotation purely for static analysis.

The Problem with .filter() and Union Types

Arrays in TypeScript often hold union types. After filtering, you expect a narrower type, but TypeScript cannot infer that from a plain boolean-returning callback. 


type Entity = Player | Enemy | null;

const entities: Entity[] = [
  new Player(),
  null,
  new Enemy(),
  null,
  new Enemy(),
];

// TypeScript infers: (Player | Enemy | null)[]  — not what we want
const withoutNulls = entities.filter((e) => e !== null);

Even though the runtime result never contains null, the type of withoutNulls is still (Player | Enemy | null)[]. Any code that uses it still has to handle null. This is where a type predicate fixes things.

⚠
Warning

Using a type assertion like as (Player | Enemy)[] after .filter() silences the error but gives TypeScript no information. If your filter logic has a bug, the assertion hides it. A type predicate is safer because it ties the narrowing to real runtime logic.

Writing a Type Predicate for .filter()

Rewrite the callback so its return type is a type predicate instead of boolean. TypeScript then uses that annotation to narrow the element type of the resulting array. 


// Type predicate: "if this returns true, e is Player | Enemy"
function isEntity(e: Entity): e is Player | Enemy {
  return e !== null;
}

// TypeScript now infers: (Player | Enemy)[]
const activeEntities = entities.filter(isEntity);

// No null checks needed — TypeScript knows
activeEntities.forEach((entity) => {
  entity.update(); // safe
});
💡
Tip

Name your predicate functions after what they confirm, not what they reject. isEnemy() is clearer than notNull() when reading a .filter() chain.

Narrowing to a Specific Subtype

Type predicates are especially useful when you want to split a union array into typed buckets for separate processing.


type Actor = Player | Enemy | Pickup;

function isEnemy(actor: Actor): actor is Enemy {
  return actor instanceof Enemy;
}

function isPickup(actor: Actor): actor is Pickup {
  return actor instanceof Pickup;
}

const actors: Actor[] = getActors();

const enemies: Enemy[]  = actors.filter(isEnemy);
const pickups: Pickup[] = actors.filter(isPickup);

// Each array has a precise type — no casting required
enemies.forEach((e) => e.patrol());
pickups.forEach((p) => p.respawn());
📌
Remember

A type predicate tells TypeScript what the type is, not what it is not. Write the affirmative: actor is Enemy, and let the filter do the negative work at runtime.

Inline Type Predicates with Arrow Functions

You can also write a type predicate inline as an arrow function. The syntax is the same; the return type annotation goes after the parameter list. 


const enemies = actors.filter(
  (actor): actor is Enemy => actor instanceof Enemy
);

This is concise for one-off filters. For predicates you reuse across the codebase, a named function is easier to read and test.

Combining Type Predicates with Optional Chaining

A common real-world pattern combines a null check with an instanceof check inside a single predicate.


type MaybeActor = Actor | undefined | null;

function isEnemy(value: MaybeActor): value is Enemy {
  return value instanceof Enemy; // instanceof returns false for null/undefined
}

const rawSlots: MaybeActor[] = scene.getSlots();
const enemies: Enemy[] = rawSlots.filter(isEnemy);
ℹ
Note

instanceof already returns false for null and undefined, so you rarely need an explicit null check inside a predicate that uses instanceof.

Summary
  • A type predicate uses the value is Type return annotation to tell TypeScript what type a variable is when the function returns true.
  • .filter() with a plain boolean callback does not narrow the array element type; a type predicate callback does.
  • Named predicate functions keep .filter() chains readable and are easy to reuse and unit-test.
  • You can write inline arrow-function type predicates for one-off filters: (x): x is Enemy => x instanceof Enemy.
  • Type predicates let you split a union array into fully typed buckets without casting, keeping type safety intact through the rest of your code.

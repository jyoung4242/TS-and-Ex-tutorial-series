Introduction

You have probably written a basic numeric enum before: a list of named constants where TypeScript automatically assigns 0, 1, 2, ... to each member. That works well for simple cases. But real codebases need more: flags that can be combined with bitwise operators, tile costs derived from constants, or event codes that mix readable strings with compact numbers. That is where heterogeneous and computed enum members come in.

A heterogeneous enum is one whose members have a mix of string and numeric values. A computed enum member is one whose value is not a plain literal but a constant expression evaluated at compile time. These two features are distinct but often appear together. By the end of this lesson you will know exactly when each is appropriate, how to write them correctly, and how to spot the subtle bugs they can introduce if you are not careful.

ℹ
Prior knowledge

This lesson assumes you already understand basic numeric and string enums. If either of those feels shaky, revisit the "Enum Basics" lesson before continuing.

A Quick Recap: Pure Numeric vs. Pure String Enums

Before mixing values, it helps to recall what each pure form gives you.

// Pure numeric enum — members auto-increment from 0
enum Direction {
  Up,     // 0
  Down,   // 1
  Left,   // 2
  Right,  // 3
}

// Pure string enum — every member must be explicitly initialized
enum AudioEvent {
  Play   = "PLAY",
  Pause  = "PAUSE",
  Stop   = "STOP",
}

Numeric enums have reverse mappings: at runtime, Direction[0] returns "Up". String enums do not. This difference matters a lot once you start mixing the two.

📌
Remember

Only numeric enum members get a reverse mapping. String members never do. This asymmetry is the root cause of most heterogeneous enum confusion.

Heterogeneous Enums: Mixing Strings and Numbers

TypeScript allows you to assign both string and numeric values inside the same enum declaration. The TypeScript documentation itself describes this as "not advised" unless you genuinely need to interop with JavaScript that already produces such mixed structures. With that caveat in mind, here is the syntax: 

enum BossState {
  Idle     = 0,
  Charging = 1,
  Dead     = "DEAD",   // string member mixed in
}

console.log(BossState.Idle);      // 0
console.log(BossState.Dead);      // "DEAD"
console.log(BossState[0]);        // "Idle"  (reverse mapping works for numeric)
console.log(BossState["DEAD"]);   // undefined — no reverse mapping for strings

The mixed enum compiles just fine. The danger is that the runtime object looks different depending on which member you inspect. Numeric members participate in the reverse mapping; string members do not. Code that iterates over Object.values(BossState) will see both the keys and the reverse-mapped values for numeric members, which produces duplicates and surprises.

⚠
Iteration surprise

Object.values(BossState) returns [0, 1, "DEAD", "Idle", "Charging"] — the numeric values, the string value, and the reverse-mapped names for the numeric members. If you iterate an enum at runtime to populate a UI or log states, use a pure string enum instead.

When heterogeneous enums are justified

There is one legitimate pattern: a boolean-like pair where you want one sentinel string and one numeric zero so that falsy checks still work: 

// Interop pattern — maps to legacy JS library values
enum LegacyFlag {
  Off = 0,
  On  = "ON",
}

// This works as a falsy check because 0 is falsy and "ON" is truthy
if (!LegacyFlag.Off) {
  console.log("flag is off"); // prints
}

Outside of JS interop scenarios like this, prefer two separate pure enums or a discriminated union instead of mixing value types in one declaration.

Computed Enum Members

A computed member's value is a constant expression that TypeScript evaluates at compile time. Computed members can reference other enum members, perform bitwise operations, use arithmetic, and call a small set of built-in functions (Math.floor is not available here; stick to bitwise and arithmetic operators). 

enum Tile {
  Empty   = 0,
  Wall    = 1 << 0,   // 1 — bit 0
  Water   = 1 << 1,   // 2 — bit 1
  Lava    = 1 << 2,   // 4 — bit 2
  Hazard  = Water | Lava, // 6 — computed from two members
}

// Check whether a tile contains lava
function isHazardous(tile: Tile): boolean {
  return (tile & Tile.Lava) !== 0;
}

console.log(isHazardous(Tile.Lava));    // true
console.log(isHazardous(Tile.Hazard));  // true
console.log(isHazardous(Tile.Wall));    // false

This pattern is called a bitmask enum (or flags enum). Each member represents a single bit, and you combine them with the bitwise OR (|) operator. Testing a combination uses bitwise AND (&).

ℹ
Constant vs. computed

TypeScript distinguishes constant members (literal values or expressions the compiler can fold at compile time) from computed members (expressions that remain as runtime code). Bitwise and arithmetic expressions over other enum members are constant. Calling functions like someArray.length produces a computed member that TypeScript cannot fold, which prevents subsequent members from auto-incrementing. Put computed members last to avoid this limitation.

The ordering constraint

Once TypeScript hits a truly computed member (one it cannot resolve at compile time), it cannot auto-increment subsequent members. This means any member after a non-constant computed member must be explicitly initialized. 

function getVersion(): number { return 3; }

enum Config {
  MaxActors   = 100,        // constant
  Version     = getVersion(), // computed (runtime call — cannot fold)
  // DoubleMax = MaxActors * 2, // ERROR: must have initializer after computed member
  DoubleCap   = 200,        // fine — explicitly initialized
}
💡
Tip: put runtime-computed members last

If you must include a member whose value comes from a function call, place it at the very end of the enum. All constant members can then auto-increment freely without being blocked.

Putting It Together: Collision Filters in ExcaliburJS

ExcaliburJS uses a numeric category and mask system to decide which actors collide with each other. Each actor is assigned a category (what it is) and a mask (what it can collide with). Bitmask enums map perfectly onto this API and eliminate the raw-number bugs that plague collision filter code. 

import * as ex from "excalibur";

// Bitmask enum — each member is a distinct bit
enum CollisionCategory {
  None    = 0,
  Player  = 1 << 0,   // 1
  Enemy   = 1 << 1,   // 2
  Bullet  = 1 << 2,   // 4
  Terrain = 1 << 3,   // 8
  Pickup  = 1 << 4,   // 16
}

// Derived masks using computed members
enum CollisionMask {
  // Player collides with enemies, terrain, and pickups — not other players or bullets
  Player  = CollisionCategory.Enemy | CollisionCategory.Terrain | CollisionCategory.Pickup,
  // Bullet collides only with enemies and terrain
  Bullet  = CollisionCategory.Enemy | CollisionCategory.Terrain,
  // Enemy collides with player and terrain
  Enemy   = CollisionCategory.Player | CollisionCategory.Terrain,
}

// Apply to actors
const player = new ex.Actor({ name: "player" });
player.body.collisionType = ex.CollisionType.Active;
player.body.group = ex.CollisionGroupManager.groupForBits(
  CollisionCategory.Player,
  CollisionMask.Player
);

const bullet = new ex.Actor({ name: "bullet" });
bullet.body.collisionType = ex.CollisionType.Active;
bullet.body.group = ex.CollisionGroupManager.groupForBits(
  CollisionCategory.Bullet,
  CollisionMask.Bullet
);

Because each category is a single bit, you can always test membership with a bitwise AND check:

function canCollideWith(actorCategory: CollisionCategory, mask: CollisionMask): boolean {
  return (mask & actorCategory) !== 0;
}

// Can a bullet hit an enemy?
console.log(canCollideWith(CollisionCategory.Enemy, CollisionMask.Bullet));   // true
// Can a bullet hit a player?
console.log(canCollideWith(CollisionCategory.Player, CollisionMask.Bullet));  // false
💡
Separate category from mask enums

Keeping CollisionCategory and CollisionMask as two separate enums makes it impossible to accidentally pass a mask where a category is expected. TypeScript's structural typing does not protect you here because both are number at runtime, but the distinct names at the call site make mistakes obvious during code review.

Heterogeneous Enums in a Game Context

Here is a scenario where a heterogeneous enum is tempting but ultimately a design smell. Imagine you want a single enum to represent both numeric priority levels and named special states: 

// Tempting but problematic
enum AIState {
  Idle      = 0,
  Patrol    = 1,
  Chase     = 2,
  Dead      = "DEAD",   // special terminal state
}

// The problem: iterating to display a debug overlay
Object.values(AIState).forEach(v => {
  console.log(v); // 0, 1, 2, "DEAD", "Idle", "Patrol", "Chase"
  //                 ^ duplicates from reverse mapping of numeric members
});

The better approach is a discriminated union or two separate constructs: a numeric enum for the active states and a separate string literal type for terminal states: 

enum ActiveAIState {
  Idle   = 0,
  Patrol = 1,
  Chase  = 2,
}

type TerminalAIState = "DEAD" | "ESCAPED";

type AIState = ActiveAIState | TerminalAIState;

function describeState(state: AIState): string {
  if (state === "DEAD")    return "Enemy is dead";
  if (state === "ESCAPED") return "Enemy has escaped";
  if (state === ActiveAIState.Chase)  return "Enemy is chasing the player";
  if (state === ActiveAIState.Patrol) return "Enemy is on patrol";
  return "Enemy is idle";
}
📌
Remember

When you feel the pull toward a heterogeneous enum, ask whether a union type or two separate enums would model the domain more clearly. The answer is almost always yes. Reserve heterogeneous enums for JavaScript interop with existing mixed-value structures.

Summary
  • A heterogeneous enum mixes string and numeric member values in one declaration. Only numeric members get reverse mappings, which makes runtime iteration produce duplicate entries and surprising results.
  • Heterogeneous enums are justified only for JavaScript interop with existing mixed-value structures. In new TypeScript code, prefer a union type or two separate pure enums.
  • A computed enum member's value is a constant expression evaluated at compile time. Bitwise and arithmetic operations over other enum members are always constant.
  • Bitmask enums use left-shift notation (1 << n) to assign each member a unique bit, enabling multiple flags to be combined with | and tested with &.
  • After a truly computed (runtime-evaluated) member, all subsequent members must have explicit initializers. Placing runtime-computed members last avoids this restriction.
  • In ExcaliburJS, bitmask enums map directly onto the collision category and mask system, turning raw numeric magic values into self-documenting named constants.

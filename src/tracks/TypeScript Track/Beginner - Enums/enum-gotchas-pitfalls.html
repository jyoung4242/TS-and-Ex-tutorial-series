Introduction

Enums look like a clean solution: a named set of values, grouped together, easy to read. They are one of the most commonly reached-for TypeScript features, especially when modeling things like game states, enemy types, or input directions. But enums carry a set of behaviors that surprise even experienced TypeScript developers, and several of those surprises show up at runtime in ways the compiler will not warn you about.

This lesson walks through the most common enum pitfalls, what actually happens under the hood, and the alternatives you can use when enum semantics become a liability. The Excalibur examples throughout this lesson reflect patterns you will encounter in real game code: direction enums, actor state machines, event type registries, and component flags.

Pitfall 1: Numeric Enums Have Reverse Mapping

When you compile a numeric enum, TypeScript emits a JavaScript object that maps names to numbers and numbers back to names. This reverse mapping is a runtime feature, not just a type system artifact. 


enum Direction {
  Up,
  Down,
  Left,
  Right,
}

// At runtime, the compiled object looks like this:
// {
//   Up: 0,    Down: 1,  Left: 2,  Right: 3,
//   0: "Up",  1: "Down", 2: "Left", 3: "Right"
// }

console.log(Direction[0]);   // "Up"
console.log(Direction["Up"]); // 0

The reverse mapping exists so you can log a friendly name at runtime. That sounds useful, but it creates a serious type-safety hole: TypeScript accepts any number as a valid enum value, even numbers that do not correspond to any member. 


enum Direction {
  Up,
  Down,
  Left,
  Right,
}

function move(dir: Direction): void {
  console.log("Moving:", Direction[dir]);
}

move(Direction.Up); // Fine: "Moving: Up"
move(99);           // Also fine at compile time! Logs: "Moving: undefined"
⚠
Warning: Numbers slip through numeric enums

TypeScript's type checker allows any number to be assigned to a numeric enum type. If you pass a raw number where an enum is expected, the compiler will not complain, but your runtime behavior may be undefined or silently wrong.

The Excalibur Angle

Suppose you model an enemy's AI state with a numeric enum in an Excalibur game. A serialized save file or a network message could send back an integer that no longer maps to a valid state because the enum was reordered in a later build. The game receives 3, which used to mean Attacking but now maps to undefined after you added a new state between members. 


// Version 1 of your code
enum EnemyState {
  Idle,      // 0
  Patrol,    // 1
  Attacking, // 2
}

// Version 2 — you added Chasing in the middle
enum EnemyState {
  Idle,      // 0
  Patrol,    // 1
  Chasing,   // 2  <-- new member shifted everything below it
  Attacking, // 3  <-- was 2, now 3
}

// Any saved value of 2 now silently means the wrong thing
📌
Remember

Inserting a member into the middle of a numeric enum silently renumbers every member that follows it. If those values ever leave your process (saves, network, logs), deserialization will silently produce wrong results.

Pitfall 2: String Enums Are Safer but Still Nominal

String enums do not get reverse mapping. Each member has an explicit string value, which means reordering members never silently changes anything, and the emitted object only maps names to strings (not the other way around). 


enum EnemyState {
  Idle      = "IDLE",
  Patrol    = "PATROL",
  Chasing   = "CHASING",
  Attacking = "ATTACKING",
}

// No reverse mapping:
// { Idle: "IDLE", Patrol: "PATROL", Chasing: "CHASING", Attacking: "ATTACKING" }

// Reordering members does NOT change values
// Safe to serialize and deserialize

However, string enums are nominal, not structural. This means a plain string that matches an enum member's value is not assignable to the enum type, even if the string is identical. 


enum EnemyState {
  Idle = "IDLE",
}

function setState(s: EnemyState): void { /* ... */ }

setState(EnemyState.Idle); // OK
setState("IDLE");           // Error: Argument of type '"IDLE"' is not assignable
                            // to parameter of type 'EnemyState'

This nominality cuts both ways. It prevents accidental mismatches, but it also means you cannot easily construct an EnemyState from a string you received from outside your codebase without an explicit cast or a type guard.

💡
Tip: Validate at the boundary

When reading enum-shaped values from an external source (a config file, a network response, a save file), write a small validation function that narrows the raw string into the enum type rather than casting with as EnemyState. This keeps the rest of your code genuinely type-safe. 


enum EnemyState {
  Idle      = "IDLE",
  Patrol    = "PATROL",
  Attacking = "ATTACKING",
}

function isEnemyState(value: string): value is EnemyState {
  return Object.values(EnemyState).includes(value as EnemyState);
}

const raw = "PATROL"; // Comes from a config file

if (isEnemyState(raw)) {
  // raw is narrowed to EnemyState here
  console.log("Valid state:", raw);
} else {
  console.error("Unknown state:", raw);
}

Pitfall 3: const enum Inlines Values at Compile Time

A const enum instructs TypeScript to erase the enum object entirely and inline each member's numeric or string value directly at every use site. No JavaScript object is emitted at all. 


const enum ActorLayer {
  Background = 0,
  Terrain    = 1,
  Enemies    = 2,
  Player     = 3,
  HUD        = 4,
}

// This TypeScript:
const layer = ActorLayer.Player;

// Compiles to this JavaScript:
const layer = 3;

This produces smaller output and removes an object lookup at runtime. For performance-sensitive game code with many layer or flag comparisons, that matters. But const enum has traps of its own.

Trap: const enum Does Not Work Across Module Boundaries in Certain Toolchains

When you use a bundler that transpiles TypeScript files in isolation (esbuild, Babel, SWC), each file is compiled without knowledge of other files. If a const enum is defined in one file and used in another, the bundler cannot inline the value because it has not seen the definition. The result is a reference to an object that does not exist at runtime. 


// actor-layers.ts
export const enum ActorLayer {
  Background = 0,
  Player     = 3,
}

// game-scene.ts (compiled in isolation by esbuild)
import { ActorLayer } from "./actor-layers";

const layer = ActorLayer.Player;
// esbuild may emit: const layer = ActorLayer.Player;
// But ActorLayer is never defined — runtime error!
⚠
Warning: const enum and isolated transpilation do not mix

If your build pipeline uses esbuild, Babel, or Vite (which uses esbuild under the hood), avoid const enum in shared modules. Use a regular enum or a plain object with as const instead.

Trap: You Cannot Iterate a const enum

Because no object is emitted, you cannot call Object.values() or Object.keys() on a const enum at runtime. If you need to iterate members (to populate a dropdown, register handlers, or validate input), a const enum is the wrong tool. 


const enum ActorLayer {
  Background = 0,
  Player     = 3,
}

// This does not work — ActorLayer does not exist at runtime
Object.values(ActorLayer).forEach(layer => {
  console.log(layer); // ReferenceError: ActorLayer is not defined
});

The Better Alternative: as const Objects

For many use cases, a plain object with as const gives you everything you want from an enum: named constants, a stable value set, and a derived type you can use for annotations. It works in every toolchain, supports iteration, and avoids all of the traps described above. 


const ActorLayer = {
  Background: 0,
  Terrain:    1,
  Enemies:    2,
  Player:     3,
  HUD:        4,
} as const;

// Derive a type from the values
type ActorLayer = typeof ActorLayer[keyof typeof ActorLayer];
// ActorLayer = 0 | 1 | 2 | 3 | 4

function setLayer(actor: Actor, layer: ActorLayer): void {
  actor.z = layer;
}

setLayer(player, ActorLayer.Player); // OK
setLayer(player, 99);                // Error: 99 is not assignable to ActorLayer

You also get safe iteration:


const ActorLayer = {
  Background: 0,
  Terrain:    1,
  Enemies:    2,
  Player:     3,
  HUD:        4,
} as const;

// Iterate at runtime — this works fine
Object.entries(ActorLayer).forEach(([name, z]) => {
  console.log(`Layer "${name}" has z-index ${z}`);
});
ℹ
Note: Enums are not always wrong

If your project compiles with tsc directly (not an isolated transpiler), and you do not need to iterate members, string enums with explicit values are safe and readable. The goal is not to avoid enums entirely, but to understand when their specific behaviors become a liability.

When a Union of Literals Is Enough

For many scenarios, especially function parameters and component props, a union of string literals is the simplest correct choice. No object is emitted, no runtime surprises, and the type is entirely self-documenting. 


// Instead of:
enum EnemyType {
  Goblin  = "GOBLIN",
  Orc     = "ORC",
  Dragon  = "DRAGON",
}

// You can write:
type EnemyType = "GOBLIN" | "ORC" | "DRAGON";

function spawnEnemy(type: EnemyType, scene: Scene): Actor {
  // ...
}

spawnEnemy("GOBLIN", scene); // Works directly — no EnemyType.Goblin needed
spawnEnemy("TROLL", scene);  // Error: '"TROLL"' is not assignable to type 'EnemyType'

The downside: you lose the grouping that an enum provides, and refactoring all occurrences of "GOBLIN" across a large codebase is slightly harder than renaming EnemyType.Goblin. For small, stable sets of values, the tradeoff almost always favors the union type. For large or frequently-referenced sets, the as const object pattern gives you the best of both worlds.

enum ProjectileType {
  Arrow,
  Fireball,
  IceShard,
  PoisonBolt,
}

function fireProjectile(type: ProjectileType): void {
  console.log("Firing type:", type);
}

  1. Convert ProjectileType to an as const object with explicit string values for each member.

Summary
  • Numeric enums allow any number to be assigned to them at compile time, making them less type-safe than they appear. An explicit string enum or as const object closes this gap.
  • Inserting a member into the middle of a numeric enum silently renumbers all subsequent members. If enum values ever leave your process, use string values or as const to keep them stable.
  • String enums are nominal: a string literal matching a member's value is not assignable to the enum type without a cast or type guard. Validate external strings at the boundary rather than casting blindly.
  • const enum inlines values at compile time but breaks in isolated transpilation pipelines (esbuild, Babel, Vite) and cannot be iterated at runtime.
  • A plain object with as const plus a derived union type gives you named constants, full type safety, runtime iteration, and compatibility with every TypeScript toolchain.
  • A union of string literals is often the simplest correct choice for small, stable value sets used in function parameters or component props.

Introduction

Strings show up everywhere in game code. An actor might be in a "idle", "running", or "dead" state. An event might carry a type of "collision" or "pickup". At first, those raw strings feel harmless — they are readable, they log nicely, and they work. The problem appears the moment you mistype "runing" or rename "dead" to "destroyed" without updating every reference. TypeScript cannot catch those mistakes when values are plain strings.

String enums solve this by binding a readable label to a fixed string value inside the type system. Once a value is declared as part of a string enum, TypeScript checks every assignment and comparison against the declared set. Mistyped values become compile errors instead of silent runtime bugs.

This lesson walks through how string enums work, where they outperform their alternatives, and how to reach for them confidently when building typed game logic with ExcaliburJS.

Declaring a String Enum

A string enum looks exactly like a numeric enum except that each member is explicitly initialised with a string value. TypeScript requires every member to have an initialiser because string enums do not auto-increment the way numeric enums do. 


enum ActorState {
  Idle    = "idle",
  Running = "running",
  Jumping = "jumping",
  Dead    = "dead",
}

// Usage: the variable is typed as ActorState, not string
let playerState: ActorState = ActorState.Idle;
console.log(playerState); // "idle"
ℹ
Note

The string value on the right side is what ends up in the compiled JavaScript and in your logs. The member name on the left (e.g. Idle) is purely a TypeScript-side label — it never appears at runtime.

Using an Enum in a Function

Once a string enum exists, you use its type exactly like any other type annotation. TypeScript will reject any value that is not a declared member. 


enum ActorState {
  Idle    = "idle",
  Running = "running",
  Jumping = "jumping",
  Dead    = "dead",
}

function onStateChange(next: ActorState): void {
  console.log(`State changed to: ${next}`);
}

onStateChange(ActorState.Running); // OK
onStateChange("running");          // Error: Argument of type '"running"'
                                   // is not assignable to parameter of
                                   // type 'ActorState'
💡
Tip

That error on the raw string "running" is intentional and desirable. Forcing callers to go through ActorState.Running means a rename in the enum definition is the single place you ever need to update.

String Enums vs. Numeric Enums

TypeScript's original enums assign numbers automatically:


// Numeric enum — members get 0, 1, 2, ...
enum Direction {
  Up,
  Down,
  Left,
  Right,
}

console.log(Direction.Up);   // 0
console.log(Direction[0]);   // "Up" — reverse mapping exists!

Numeric enums support reverse mapping: you can look up a member name from its numeric value. This sounds convenient, but it means the compiled JavaScript object has twice as many keys as you declared, which can produce surprising results when you iterate over an enum or serialise it. 


// String enum — NO reverse mapping
enum ActorState {
  Idle = "idle",
  Dead = "dead",
}

// ActorState["idle"] does NOT exist — string enums are one-directional
// This keeps the compiled output clean and predictable
console.log(Object.keys(ActorState)); // ["Idle", "Dead"]
⚠
Warning

If you iterate over a numeric enum expecting only the member names, you will also get the numeric keys. String enums skip the reverse mapping entirely, so Object.keys(ActorState) returns exactly the names you declared and nothing more.

String Enums vs. Union Types

A union of string literals is another common TypeScript pattern that looks similar to a string enum:


// Union of string literals
type ActorStateUnion = "idle" | "running" | "jumping" | "dead";

// String enum
enum ActorState {
  Idle    = "idle",
  Running = "running",
  Jumping = "jumping",
  Dead    = "dead",
}

Both give you type safety on assignments and comparisons. The differences matter when you choose between them:

  • Union types accept the raw string value (e.g. "idle") wherever the type is expected. This is often more ergonomic for public-facing APIs.
  • String enums reject raw string values and require the enum member reference (e.g. ActorState.Idle). This enforces a single canonical reference point across a codebase.
  • String enums produce a real JavaScript object at runtime, meaning you can iterate over ActorState, store it, or pass it to a function that expects an object. Union types are erased entirely at compile time.
📌
Remember

Prefer a union type when the set of strings is part of a public API that callers should be able to satisfy with plain string literals. Prefer a string enum when you own both sides of the code and want a single named reference that travels with the compiled JavaScript.

String Enums vs. as const Objects

A third alternative is a plain object marked with as const:


const ActorState = {
  Idle:    "idle",
  Running: "running",
  Jumping: "jumping",
  Dead:    "dead",
} as const;

// Derive the union of values for use as a type
type ActorStateType = typeof ActorState[keyof typeof ActorState];
// "idle" | "running" | "jumping" | "dead"

This pattern is popular in codebases that avoid enums for philosophical reasons (enums are not standard JavaScript). It provides the same runtime object and a derived union type, but the ergonomics require a separate type alias. String enums bundle the object and the type together in a single declaration.

ℹ
Note

Neither choice is universally superior. Teams that strictly follow the "TypeScript is just annotated JavaScript" philosophy often prefer as const objects. Teams that treat TypeScript as its own language often prefer string enums for their concision. Either way, pick one and stay consistent.

String Enums in Switch Statements

String enums pair especially well with switch statements because the compiler can check that every case is handled. If you add a new state to the enum and forget to add a corresponding case, TypeScript can warn you via an exhaustiveness check. 


enum ActorState {
  Idle    = "idle",
  Running = "running",
  Jumping = "jumping",
  Dead    = "dead",
}

function getAnimationFrame(state: ActorState): string {
  switch (state) {
    case ActorState.Idle:    return "frame_idle_00";
    case ActorState.Running: return "frame_run_00";
    case ActorState.Jumping: return "frame_jump_00";
    case ActorState.Dead:    return "frame_dead_00";
    default:
      // This branch is only reachable if a new enum member is added
      // without a matching case above.
      const _exhaustiveCheck: never = state;
      return _exhaustiveCheck;
  }
}
💡
Tip

Assigning the unmatched value to a never variable in the default branch is called an exhaustiveness check. If the switch is complete, TypeScript is satisfied because the default branch is unreachable. If a new enum member is added and has no case, the assignment to never becomes a compile error, alerting you immediately.

Summary
  • A string enum binds a TypeScript label to a fixed string value, letting the compiler catch typos and missing updates at build time.
  • Unlike numeric enums, string enums have no reverse mapping, so iterating over them produces only the member names you declared.
  • String enums reject raw string values at assignment and call sites; callers must reference the enum member, which creates a single source of truth for the value.
  • Union types are a lighter-weight alternative when callers should be able to pass plain string literals; as const objects are an alternative when you want to stay closer to plain JavaScript.
  • Pairing a string enum with a switch exhaustiveness check ensures every member is handled and turns missing cases into compile errors rather than silent runtime bugs.
